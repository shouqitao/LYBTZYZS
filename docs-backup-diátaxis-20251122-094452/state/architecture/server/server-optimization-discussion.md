## 📋 需求概述

**业务目标**: 优化LYBT.Server端架构，消除过度设计，提升开发效率和维护性，同时保持所有现有业务功能的完整性。

**目标用户**: 开发团队、架构师、系统维护人员

**核心背景**:
- 当前Server端存在BaseApiController过度设计（529行，31个重复方法）
- 响应格式过度统一导致30-50%数据传输冗余
- MedicalCase模块API端点过多（16个），存在功能重叠
- 权限验证逻辑重复，缺乏统一管理
- Service层存在不必要的双重映射开销

**优化愿景**: 构建简洁、高效、易维护的Server端架构，保持业务逻辑完整性的同时，显著提升开发效率和系统性能。

## ✨ 功能性需求

### FR-001: BaseApiController重构
**描述**: 简化BaseApiController，消除过度设计的重复响应方法

**User Story**:
```
作为 开发团队
我想要 简洁的BaseApiController基类
以便 快速理解和使用，减少学习成本
```

**验收标准**:
- [x] 将BaseApiController从529行代码减少到50行左右（减少90%）
- [x] 将31个重复的响应方法合并为4-5个核心方法
- [x] 保持所有Controller的功能完整性
- [x] 确保新旧Controller接口兼容性

### FR-002: 响应格式差异化优化
**描述**: 根据数据大小智能选择响应格式，减少不必要的传输冗余

**User Story**:
```
作为 系统用户
我想要 高效的数据传输
以便 减少网络传输时间，提升使用体验
```

**验收标准**:
- [x] 大数据（≥1KB）直接返回，无额外包装
- [x] 小数据（<1KB）使用简化包装格式
- [x] 平均数据传输效率提升33%
- [x] 客户端调用方式保持不变

### FR-003: MedicalCase模块API优化
**描述**: 合并功能重叠的API端点，简化接口设计

**User Story**:
```
作为 前端开发人员
我想要 简洁清晰的MedicalCase API
以便 减少集成复杂度，提高开发效率
```

**验收标准**:
- [x] 将MedicalCase Controller从16个端点减少到10个（减少37.5%）
- [x] 合并功能相似的端点（如CompleteMedicalCase和CloseMedicalCase）
- [x] 统一更新接口，支持多种操作类型
- [x] 保持所有业务功能的完整性

### FR-004: 权限验证统一化
**描述**: 建立统一的权限验证机制，消除重复代码

**User Story**:
```
作为 开发人员
我想要 统一的权限验证机制
以便 减少重复代码，降低维护成本
```

**验收标准**:
- [x] 创建BaseService基类，统一权限验证逻辑
- [x] 实现权限验证中间件，避免Controller层重复
- [x] 权限验证重复代码减少80%以上
- [x] 保持现有权限规则不变

### FR-005: Service层双重映射优化
**描述**: 优化Service层的DTO映射策略，减少不必要的转换开销

**User Story**:
```
作为 系统架构师
我想要 高效的数据映射策略
以便 提升系统性能，减少资源消耗
```

**验收标准**:
- [x] 识别并消除不必要的DTO→Entity→DTO双重映射
- [x] Service层平均处理时间减少15-20%
- [x] 保持接口契约的稳定性
- [x] 不影响现有业务逻辑

### FR-006: 统一业务规则验证
**描述**: 建立集中的业务规则验证机制，提高代码复用性

**User Story**:
```
作为 业务开发人员
我想要 可复用的业务规则验证
以便 避免重复实现，确保规则一致性
```

**验收标准**:
- [x] 创建BusinessRuleValidator类，集中管理验证规则
- [x] 统一MedicalCase、Prescription等模块的业务规则
- [x] 业务规则验证代码复用率提升70%
- [x] 验证逻辑与业务逻辑分离

## 📐 业务规则

### BR-001: 渐进式重构原则
- **规则**: 所有重构必须分阶段实施，确保系统稳定
- **理由**: 避免大规模变更带来的风险
- **实现**: 分Phase实施，每阶段完成后进行完整测试

### BR-002: 业务完整性保证
- **规则**: 重构过程中不能破坏任何现有业务功能
- **理由**: 医疗系统的业务逻辑完整性至关重要
- **实现**: 每个功能变更后进行完整回归测试

### BR-003: 架构约束遵循
- **规则**: 必须保持三层架构，不引入新的框架或技术
- **理由**: 遵循MVP原则，避免技术膨胀
- **实现**: 重构仅优化现有实现，不改变架构模式

### BR-004: 数据一致性保证
- **规则**: 重构不能影响数据完整性和一致性
- **理由**: 医疗数据的准确性不可妥协
- **实现**: 所有Repository和Entity操作保持原有语义

### BR-005: 接口契约稳定性
- **规则**: 公开API接口的契约不能破坏性变更
- **理由**: 前端依赖稳定性
- **实现**: 新旧接口并存，逐步迁移

## 🏗️ 架构约束

### 技术栈限制（基于MVP Constitution）
- ✅ **架构模式**: 三层架构（Controller → Service → Repository）
- ✅ **数据访问**: Entity Framework Core 8.0
- ✅ **Web框架**: ASP.NET Core Web API
- ✅ **数据库**: SQL Server
- ❌ **禁止引入**: Redis、RabbitMQ、MediatR、CQRS等分布式架构组件

### 架构层分配
- **Presentation Layer**: Controllers优化，统一响应格式
- **Application Layer**: Services重构，统一权限验证和业务规则
- **Infrastructure Layer**: Repositories保持，优化查询性能

### 重构范围
- **全局优化**: BaseApiController、响应格式、权限验证
- **模块优化**: MedicalCase（重点）、Prescription、Patient、Users等
- **服务优化**: Service层映射策略、业务规则验证

## ❓ 开放问题

### Q1: BaseApiController的迁移策略
**问题**: 如何处理大量现有Controller的基类切换？

**选项**:
- A. 一次性全部切换（快速但有风险）
- B. 分批逐步切换（安全但周期长）
- C. 保留新旧基类并存（过渡期最长）

**建议**: 选B（分批切换，从简单Controller开始）

### Q2: 响应格式变化的客户端影响
**问题**: 响应格式差异化是否影响前端解析？

**选项**:
- A. 完全透明（前端无感知）
- B. 提供客户端SDK
- C. 配置化响应格式

**建议**: 选A（保持完全向后兼容）

### Q3: MedicalCase API合并的兼容性
**问题**: API端点合并后如何处理已废弃的端点？

**选项**:
- A. 立即删除（激进）
- B. 标记废弃保留6个月（推荐）
- C. 永久保留（保守）

**建议**: 选B（标记[Obsolete]，保留过渡期）
