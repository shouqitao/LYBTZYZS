# Proposal: coverage-driven-cleanup

## Summary

基于代码覆盖率分析的彻底代码清理任务。使用coverlet.collector收集单元测试覆盖率数据，识别零覆盖的类和方法，结合引用分析确认死代码，进行系统性清理。

## Why

1. 测试覆盖率基础设施已配置但测试项目未引用coverlet.collector
2. 死代码识别依赖人工grep分析，可能遗漏
3. 缺乏覆盖率基准数据用于持续监控

## What Changes

1. 所有测试项目添加coverlet.collector引用
2. 优化.runsettings覆盖率收集配置
3. 创建覆盖率收集脚本
4. 建立覆盖率基准文档

## Motivation

### 当前问题

1. **测试覆盖率基础设施已配置但未充分利用**
   - `.runsettings`已配置XPlat Code Coverage
   - `coverlet.collector 6.0.4`已在Directory.Packages.props定义
   - 但测试项目未引用coverlet.collector包

2. **死代码识别依赖人工分析**
   - 之前的死代码清理（optimize-desktop-core Phase 1）依赖grep引用分析
   - 删除了30+个死代码文件（Foundation 10个 + Infrastructure 19个 + Tests 2个）
   - 但可能仍有未被识别的死代码

3. **缺乏覆盖率驱动的持续监控**
   - 没有基准线覆盖率数据
   - 无法追踪覆盖率变化趋势
   - 难以识别"从未被测试"的代码路径

### 预期收益

- 识别零覆盖的公开类和方法（潜在死代码）
- 建立覆盖率基准线（line coverage / branch coverage）
- 减少代码库体积，提升可维护性
- 为后续开发提供覆盖率参考

## Goals

1. **配置覆盖率收集基础设施** - 所有测试项目引用coverlet.collector
2. **生成完整覆盖率报告** - 运行全部测试并生成Cobertura/OpenCover格式报告
3. **分析零覆盖代码** - 识别从未被执行的类和方法
4. **验证并清理死代码** - 结合引用分析确认后删除
5. **建立覆盖率基准** - 记录当前覆盖率作为参考基准

## Non-Goals

- 不追求特定覆盖率百分比目标
- 不编写新测试（仅用于识别死代码）
- 不重构现有代码结构
- 不集成CI/CD覆盖率门禁

### 覆盖率收集配置

**当前.runsettings排除规则**:
```xml
<Exclude>[*.Tests]*,[*]*.Designer,[*]*.g.cs</Exclude>
```

**优化后的排除规则**:
```xml
<Exclude>
  [*.Tests]*,
  [*]*.Designer,
  [*]*.g.cs,
  [*]*.Generated,
  [*]AutoGeneratedProgram,
  [LYBT.WebAPI]Program,
  [*]*.Migrations.*
</Exclude>
```

### 覆盖率报告输出

- **格式**: Cobertura (机器解析) + OpenCover (详细分析)
- **输出目录**: `BIN/TestResults/Coverage/`
- **HTML报告**: 使用ReportGenerator生成可视化报告

## Implementation Phases

### Phase 1: 配置覆盖率收集 (0.5天)

**任务**:
1. 更新所有测试项目添加coverlet.collector引用
2. 优化.runsettings排除规则
3. 创建覆盖率收集脚本

**变更文件**:
- `tests/**/*.csproj` (36个测试项目)
- `tests/.runsettings`
- 新增 `scripts/collect-coverage.ps1`

### Phase 2: 运行覆盖率分析 (0.5天)

**任务**:
1. 执行全量测试收集覆盖率
2. 合并覆盖率报告
3. 生成HTML可视化报告

**命令示例**:
```bash
dotnet test LYBT.All.sln --settings tests/.runsettings --collect:"XPlat Code Coverage" --results-directory BIN/TestResults
reportgenerator -reports:"BIN/TestResults/**/coverage.cobertura.xml" -targetdir:"BIN/TestResults/CoverageReport" -reporttypes:"Html;Cobertura"
```

### Phase 3: 识别零覆盖代码 (1天)

**任务**:
1. 解析Cobertura XML报告
2. 提取line-rate=0的类列表
3. 分类整理候选清理项
4. 排除合理的零覆盖（如接口、DTO、配置类）

**输出**:
- `docs/analysis/coverage-zero-classes.md` - 零覆盖类清单
- 按模块分类的候选清理列表

### Phase 4: 验证并清理 (2-3天)

**任务**:
1. 对每个候选类执行引用分析
2. 确认真正的死代码
3. 执行清理（删除文件、更新DI注册）
4. 增量构建验证

**风险缓解**:
- 每清理5-10个文件后执行一次全量构建
- 保留git历史以便回滚

### Phase 5: 记录基准 (0.5天)

**任务**:
1. 记录清理后的覆盖率指标
2. 更新README或docs说明
3. 创建可重复使用的分析脚本

## Risks and Mitigations

| 风险项 | 概率 | 影响 | 缓解措施 |
|-------|-----|-----|---------|
| 零覆盖代码实际被使用（反射/动态加载） | 低 | 运行时异常 | 引用分析双重确认 |
| 测试运行时间过长 | 中 | 延迟进度 | 分批运行测试 |
| 覆盖率报告合并失败 | 低 | 数据不完整 | 使用ReportGenerator官方工具 |
| 清理导致编译失败 | 中 | 阻断开发 | 增量清理+频繁验证 |

## Alternatives Considered

### 方案A: 仅继续手动grep分析
继续使用grep搜索引用来识别死代码。
**否决原因**: 不可靠，容易遗漏动态引用的代码。

### 方案B: 使用静态分析工具（如ReSharper）
使用IDE内置的死代码检测功能。
**否决原因**: 需要商业许可证，且不提供覆盖率数据。

### 方案C: 覆盖率驱动分析（选定）
结合覆盖率数据和引用分析双重验证。
**选择原因**: 数据驱动，可量化，可追踪。
