# Proposal: clarify-cancel-consultation-logic

## Summary
明确"取消看诊"与"暂停看诊"的业务语义区分，确保医案生命周期管理符合诊所实际工作流程。

## Why

### 问题背景
当前系统中"取消看诊"和"暂停看诊"的语义区分不够明确：
- Issue #2242 已将 `Cancelled` 状态废弃，改用软删除（`IsDeleted=true`）
- 但UI和代码中的术语使用不够统一
- 用户对两种操作的预期行为可能产生混淆

### 业务场景分析

| 场景 | 操作 | 预期行为 |
|------|------|----------|
| 医生需要暂时离开（上厕所、接电话） | 暂停看诊 | 保存所有数据，状态→Draft，可随时继续 |
| 急诊插队，当前患者需要等待 | 暂停看诊 | 保存所有数据，状态→Draft，可随时继续 |
| 患者临时有事离开，本次就诊作废 | 取消看诊 | 软删除，数据保留供审计，不可直接继续 |
| 发现患者信息错误，需要重新开始 | 取消看诊 | 软删除，数据保留供审计，重新创建新医案 |

### 当前实现分析

**已正确实现**:
1. `MedicalCaseLifecycleHandler.CancelAsync()` 使用软删除
2. `MedicalCaseLifecycleHandler.SaveDraftAsync()` 保存到 Draft 状态
3. `MedicalCaseStatus` 枚举中 `Cancelled` 已标记为 `[Obsolete]`

**需要改进**:
1. UI提示信息不够清晰（当前提示"未保存的数据将丢失"不准确）
2. 缺少明确的业务规则文档
3. 取消操作前是否应该先保存当前数据（供审计）？

## What Changes

### 变更范围

1. **UI文案优化**: 明确取消/暂停的区别和后果
2. **取消前自动保存**: 取消操作前先保存当前数据，确保审计完整性
3. **Spec规范**: 创建正式的业务规则规范文档

### 不变更

- 软删除机制保持不变（`IsDeleted=true`）
- 状态机保持不变（`Draft ↔ Active → Completed`）
- 不添加新的状态枚举值

## Design Decisions

### 决策1: 取消操作前是否自动保存

**选项A**: 取消前自动保存所有已填写数据
- 优点: 审计数据完整，可追溯用户填写了什么
- 缺点: 增加一次网络请求，可能保存无效数据

**选项B**: 取消前不保存，直接软删除（当前实现）
- 优点: 操作快速，不保存可能无效的数据
- 缺点: 丢失用户已填写但未手动保存的内容

**推荐**: 选项A - 取消前自动保存，确保审计完整性

### 决策2: 软删除的医案是否可恢复

**选项A**: 管理员可通过后台恢复
- 优点: 灵活，可处理误操作
- 缺点: 增加复杂度

**选项B**: 不可恢复，只能查看（当前实现）
- 优点: 简单，符合"取消=作废"语义
- 缺点: 误操作无法挽回

**推荐**: 保持选项B，但在确认对话框中明确说明不可恢复
