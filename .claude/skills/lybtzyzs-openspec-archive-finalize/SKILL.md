# OpenSpec 归档完成处理器

## 核心能力

1. **代码审查** - 检查归档变更涉及的代码质量
2. **提交推送** - 审查通过后自动commit并push到远程仓库
3. **保存记忆** - 将变更关键信息保存到Serena记忆系统
4. **文档同步** - 遵循文档层级同步更新项目文档

## 文档层级（核心设计）

```
┌─────────────────────────────────────────────────────────────┐
│  openspec/project.md (权威源 - Source of Truth)            │
│  ─────────────────────────────────────────────────────────  │
│  • 项目配置、技术栈、架构规范                                 │
│  • 所有架构决策的唯一真相来源                                 │
│  • 手动维护，每次架构变更必须更新                             │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼ 同步关键信息
┌─────────────────────────────────────────────────────────────┐
│  README.md (用户入口 - User Entry Point)                    │
│  ─────────────────────────────────────────────────────────  │
│  • 项目介绍、快速开始、目录结构                               │
│  • 从project.md同步：技术栈、模块列表、目录结构                │
│  • 保持简洁，详细内容指向project.md                          │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼ 追加记录
┌─────────────────────────────────────────────────────────────┐
│  CHANGELOG.md (变更历史 - Change History)                   │
│  ─────────────────────────────────────────────────────────  │
│  • 按日期记录所有变更                                        │
│  • 每次归档自动追加记录                                      │
└─────────────────────────────────────────────────────────────┘
```

## 何时使用

- OpenSpec执行阶段(/lybtzyzs-openspec-apply)完成后触发
- OpenSpec归档（/openspec:archive）完成后手动触发
- 批量归档后需要统一处理

## 前置条件

- `openspec/changes/{change-id}/` 目录已存在
- 执行阶段已完成，所有代码变更已应用
- 用户已确认执行结果

```

│  STEP 1: 代码审查                                            │
│  ─────────────────                                          │
│  • 获取归档变更涉及的文件（git diff）                          │
│  • 执行代码规范检查（命名/MVVM/DI/异步/注释）                   │
│  • 生成审查报告（评分>=8.0通过）                              │
└──────────────────────────────────────────────────────────────┘
                              │
                    ┌─────────┴─────────┐
                    │                   │
               审查通过              审查失败
                    │                   │
                    ▼                   ▼
┌───────────────────────┐    ┌─────────────────────────────────┐
│  STEP 2: 提交推送     │    │  输出问题报告，停止流程           │

│  • git add -A         │    └─────────────────────────────────┘
│  • git commit         │
│  • git push           │
└───────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────────────────────────┐
│  STEP 3: 保存Serena记忆                                      │
│  ─────────────────────────                                  │
│  • 提取变更关键信息（change-id, 影响范围, 技术决策）            │
│  • 保存到 .serena/memories/openspec-{change-id}-{date}.md    │
└──────────────────────────────────────────────────────────────┘
                              │

┌──────────────────────────────────────────────────────────────┐
│  STEP 4: 文档同步（遵循文档层级）                              │

│  4.1 检测project.md是否需要更新                              │
│      ┌────────────────────────────────────────────────────┐ │
│      │ 检测条件（任一满足则提示）:                          │ │
│      │ • 技术栈变更（新增/移除/替换依赖）                   │ │
│      │ • 模块结构变更（新增/移除/重命名模块）               │ │
│      │ • 架构规范变更（新增/修改约定）                      │ │
│      │ • OpenSpec规范变更（新增spec文件）                   │ │
│      └────────────────────────────────────────────────────┘ │

│      ┌────────────────────────────────────────────────────┐ │

│  4.4 提交文档更新                                            │
│      → git add && git commit && git push                     │

                              │
                              ▼
┌──────────────────────────────────────────────────────────────┐
│  完成：输出处理报告                                           │
└──────────────────────────────────────────────────────────────┘
```

## 输入要求

**必需**：
- `change_id` - 变更ID（通过skill参数传入）

**可选**：
- `skip_review` - 跳过代码审查（默认false，仅紧急情况使用）
- `skip_docs` - 跳过文档同步（默认false）
- `dry_run` - 模拟运行，不实际提交（默认false）

## 输出格式

```markdown
## OpenSpec 归档完成处理报告

**变更ID**: {change-id}
**归档时间**: {timestamp}
**处理状态**: 成功/失败

---

### 1. 代码审查结果

**评分**: {score}/10
**检查文件**: {file-count}个
**问题统计**: 严重{critical} / 警告{warning} / 通过{passed}

---

### 2. 提交推送结果

**提交哈希**: {commit-hash}
**推送状态**: 成功/失败

---

### 3. Serena记忆保存

**记忆文件**: `.serena/memories/openspec-{change-id}-{date}.md`

---

### 4. 文档同步结果

**project.md状态**:
- 无需更新 / 建议更新
- （若建议更新）原因：{reason}

**README.md状态**:
- 已同步 / 已是最新 / 需手动检查

```

## project.md更新检测规则

### 触发检测的变更类型

| 变更类型 | 需要更新的section | 关键词示例 |
|----------|-------------------|------------|
| 新增依赖包 | Tech Stack | Mapperly, Riok, 新增包引用 |
| 移除依赖包 | Tech Stack | 移除AutoMapper, 删除依赖 |
| 新增模块 | Solution Structure | 新增Desktop.Printing模块 |
| 移除模块 | Solution Structure | 删除Desktop.Prescriptions |
| 重命名模块 | Solution Structure | 重命名为xxx |
| 架构模式变更 | Architecture Conventions | 新增Mapping约定, 标准化xxx |
| 新增OpenSpec规范 | OpenSpec Specifications | 新增spec文件 |

### 检测逻辑

```
1. 读取归档的proposal.md内容
2. 检查关键词匹配：
   - 技术栈：依赖、包、库、框架、替换、迁移、NuGet
   - 模块结构：新增模块、删除模块、重命名、迁移到、移除
   - 架构规范：约定、规范、模式、标准化、Convention
3. 若检测到，生成具体更新建议
4. 输出提示信息，由用户决定是否更新
```

## README.md同步检查项

### 同步映射关系

| project.md section | README.md section | 同步策略 |
|--------------------|-------------------|----------|
| Tech Stack | 技术栈 | 同步依赖包列表和版本号 |
| Solution Structure | 项目结构 | 同步目录树和模块说明 |
| Module Status | 功能模块 | 同步模块状态（已实现/开发中） |

### 同步策略

1. **检测差异**: 比对project.md与README.md的关键section
2. **增量更新**: 仅更新有差异的部分
3. **保持格式**: 保留README.md的整体结构和风格
4. **简洁原则**: README.md保持简洁，详细内容链接到project.md

## 代码审查标准

| 检查项 | 通过条件 |
|-------|---------|
| 命名规范 | PascalCase/\_camelCase符合标准 |
| MVVM模式 | ViewModel不直接操作UI |
| DI规范 | 无ServiceLocator反模式 |
| 异步模式 | 无.Wait()/.Result阻塞 |
| 中文注释 | 公开API有中文注释 |

**通过标准**: 评分 >= 8.0/10 且无严重问题

## Serena记忆文件结构

**文件位置**: `.serena/memories/openspec-{change-id}-{date}.md`

**内容模板**:

```markdown
# OpenSpec归档: {change-id}

**归档日期**: {date}
**提交哈希**: {commit-hash}

{summary}

## 影响范围
```

## 错误处理

| 场景 | 处理方式 |
|-----|---------|
| 代码审查失败 | 输出问题报告，停止流程 |
| git push失败 | 保留本地提交，提示手动解决 |
| 记忆目录不存在 | 自动创建`.serena/memories/`目录 |
| project.md需更新 | 输出建议，**不自动修改**（权威源需手动维护） |
| README.md同步失败 | 输出差异，提示手动检查 |

## 最佳实践

1. **project.md是权威源** - 架构变更先手动更新project.md，再运行归档流程
2. **README.md保持同步** - 每次归档自动检查并同步
3. **归档前确保代码质量** - 在归档前先执行代码审查
4. **记忆文件命名规范** - 使用`openspec-{change-id}-{date}.md`格式

## 工作流整合

此Skill是OpenSpec全流程自动化的第4阶段（最终阶段）:

```
lybtzyzs-openspec-proposal (采访阶段)
    ↓ 用户确认提案
lybtzyzs-openspec-design (设计阶段)
    ↓ 用户确认设计
lybtzyzs-openspec-apply (执行阶段)
    ↓ 用户确认完成
lybtzyzs-openspec-archive-finalize (归档阶段) ← 当前
    ↓
完成
```

### 从执行阶段过渡

执行阶段完成后，用户确认"确认完成，进入归档"即可触发此Skill:

```markdown
## 执行摘要

所有任务已完成，编译验证通过。

**选项**:
A. 确认完成，进入归档阶段  → 触发此Skill
B. 需要额外修改
C. 回滚变更
```

### 归档完成后

归档完成后，OpenSpec变更流程结束。输出完整报告供用户存档。
