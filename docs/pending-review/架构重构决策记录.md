# 架构重构决策记录

## 日期：2025-01-30

### 背景
在分析前端 Info 类与后端 Model 不对应的情况时，发现了多个需要重构的架构问题。

## 重构决策

### 1. ConsultationInfo 整合到 RecordModel
**问题**：前端有 ConsultationInfo 和 ConsultationRecord 类，但后端没有对应的 Model

**决策**：
- 删除前端的 Consultation 相关类
- 看诊信息整合到 RecordModel（病历）中
- RecordModel 已包含主诉、诊断、治疗建议等看诊核心信息

**理由**：
- 避免概念重复
- 病历（Record）本身就是看诊的记录
- 简化数据模型

### 2. 理疗功能重新设计
**问题**：前端有完整的 PhysiotherapyModels，但后端的 TreatmentRoomModel 设计不匹配

**决策**：
- 重新设计 TreatmentRoomModel 为理疗项目管理（而非治疗任务）
- 新增 TreatmentExecutionModel 记录理疗执行情况
- 在 RecordModel 中关联理疗项目

**新设计**：
```csharp
// 理疗项目目录
public class TreatmentRoomModel {
    public Guid Id { get; set; }
    public string Code { get; set; }  // 项目编码
    public string Name { get; set; }  // 项目名称
    public string Category { get; set; }  // 分类：针灸、推拿、理疗等
    public decimal Price { get; set; }
    public int Duration { get; set; }  // 时长(分钟)
    public string Description { get; set; }
}

// 理疗执行记录
public class TreatmentExecutionModel {
    public Guid Id { get; set; }
    public Guid RecordId { get; set; }  // 关联病历
    public Guid TreatmentRoomId { get; set; }  // 关联理疗项目
    public Guid TherapistId { get; set; }  // 理疗师
    public DateTime ExecutionTime { get; set; }
    public string Status { get; set; }
}
```

### 3. Payment 统一为 Billing
**问题**：前端使用 PaymentInfo，后端使用 BillingModel

**决策**：统一使用 Billing（账单）命名

**理由**：
- Billing 更准确地表达了业务概念
- 与后端保持一致

### 4. 统计功能延后开发
**问题**：前端有多个统计类，但实际使用中统计功能特别重要

**决策**：
- 删除独立的统计类（ConsultationStatistics、PhysiotherapyStatisticsInfo 等）
- 在列表页面显示基础统计信息
- 完整统计功能列入开发计划

**理由**：
- 避免过度设计
- 快速交付核心功能
- 为未来扩展预留空间

### 5. 离线同步功能延后开发
**问题**：后端有 SyncLogModel 和 SyncTaskModel，设计用于离线同步

**决策**：
- 暂不实现前端支持
- 列入长期开发计划

**理由**：
- 离线同步是复杂特性
- 需要更多需求分析
- 优先完成核心功能

### 6. AdminSecretModel 仅后端使用
**说明**：AdminSecretModel 用于单独存储管理员密码哈希，是安全机制

**决策**：不需要前端界面，仅后端内部使用
