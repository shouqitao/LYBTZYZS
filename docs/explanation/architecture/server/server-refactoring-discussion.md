## 📋 需求概述

### 1.1 项目背景

凌隐宝堂中医诊所项目 (LYBTZYZS) 是一个企业级中医诊所管理系统，采用 .NET 8 + WPF + EF Core 技术栈。经过3年的快速发展，Server端代码出现了一些设计不合理的地方，需要进行系统性重构。

### 1.2 重构目标

- **主要目标**: 不改变当前功能的前提下，优化Server端架构设计
- **质量目标**: 提升代码可维护性、性能和开发效率
- **技术目标**: 删除无用代码，简化依赖关系，统一设计模式

## 🎯 功能性需求

### FR-1: Repository层优化
**需求描述**: 简化Repository层设计，消除过度抽象

**具体要求**:
- 分析BaseRepository的设计合理性
- 识别未使用的Repository方法和类
- 优化Repository接口设计，遵循接口隔离原则
- 统一Repository模式实现

**验收标准**:
- [ ] BaseRepository代码行数减少50%以上
- [ ] 所有Repository方法都有明确的使用场景
- [ ] Repository接口职责单一，符合ISP原则
- [ ] 单元测试覆盖率达到80%

### FR-2: Service层重构
**需求描述**: 重构Service层，解决职责混乱问题

**具体要求**:
- 分析每个Service的职责边界
- 解决Service层代码重复问题
- 优化Service间的依赖关系
- 统一Service层异常处理模式

**验收标准**:
- [ ] 每个Service类不超过300行代码
- [ ] Service间循环依赖为零
- [ ] 业务逻辑与数据访问分离清晰
- [ ] 所有Service都有对应的单元测试

### FR-3: Controller层简化
**需求描述**: 简化Controller层，提升API设计质量

**具体要求**:
- 分析Controller的职责范围
- 优化API端点设计，遵循RESTful规范
- 统一异常处理和响应格式
- 简化验证逻辑，移到Service层

**验收标准**:
- [ ] 每个Controller不超过200行代码
- [ ] 所有API端点符合RESTful设计原则
- [ ] 统一的错误响应格式

### FR-4: 依赖注入优化

**具体要求**:

## 📋 业务规则

### BR-1: Repository模式规则
- Repository只负责数据访问，不包含业务逻辑
- 每个聚合根对应一个Repository
- Repository接口遵循接口隔离原则
- 禁止在Repository中直接调用其他Service

### BR-2: Service层规则
- Service层负责业务逻辑处理
- Service之间禁止循环依赖
- 业务规则必须在Service层实现
- 异常处理统一在Service层进行

### BR-3: Controller层规则
- Controller只负责HTTP请求处理
- 禁止在Controller中包含业务逻辑
- 统一使用DTO进行数据传输
- API响应格式统一

### BR-4: 依赖注入规则
- 接口优先原则，依赖抽象而非具体实现
- 生命周期管理合理（Singleton/Scoped/Transient）
- 避免服务定位器反模式
- 配置简洁明了

## ⚠️ 架构约束

### AC-1: 技术栈约束
- 必须使用.NET 8.0
- 必须使用Entity Framework Core 8.0
- 必须使用ASP.NET Core Web API
- 数据库必须使用SQL Server

### AC-2: 设计模式约束
- 必须遵循Repository模式
- 必须遵循Service层模式
- 必须遵循依赖倒置原则
- 必须遵循单一职责原则

### AC-3: 禁止技术黑名单
根据项目MVP原则，禁止使用以下技术：
- ❌ CQRS/MediatR（过度工程）
- ❌ 微服务架构（单体足够）
- ❌ Redis（MemoryCache足够）
- ❌ 消息队列（同步处理足够）
- ❌ Docker/K8s（传统部署足够）
- ❌ GraphQL（RESTful足够）

### AC-4: 代码规范约束
- 必须遵循项目编码规范
- 必须使用异步编程模式（async/await）
- 所有数据库操作必须异步
- 必须使用LINQ进行数据查询

## 🚧 风险评估

### 高风险项
1. **BaseRepository重构**: 影响范围广，需要全面测试
2. **依赖关系调整**: 可能影响模块间通信
3. **性能优化**: 需要充分测试验证

### 中风险项
1. **Service层重构**: 业务逻辑复杂，需要仔细验证
2. **Controller简化**: API兼容性需要保证
3. **代码清理**: 可能影响现有功能

### 缓解措施
- 分阶段实施，降低单次变更风险
- 充分的自动化测试覆盖
- 详细的回滚计划
- 持续的性能监控
