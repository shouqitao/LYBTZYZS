# 代码审查指南 - AI 双审查 + 人工审查

**目的**: 规范代码审查流程，明确 AI 自动审查与人工审查的职责分工，提升代码质量。

**相关**: Issue #935 - GitHub Pro 双审查机制配置

---

## 🔍 审查流程概览

```
┌─────────────┐
│  开发者提交 PR │
└──────┬──────┘
       ↓
┌──────────────────────────────────────────┐
│  🤖 第一阶段: Claude Code 自动初审       │
│  触发: PR 创建/更新                      │
│  时间: ~2-5 分钟                         │
│  重点: 代码质量、架构合规、安全性        │
└──────┬───────────────────────────────────┘
       ↓
┌──────────────────────────────────────────┐
│  🤖 第二阶段: GitHub Copilot 二审        │
│  触发: PR 创建/更新                      │
│  时间: ~1-3 分钟                         │
│  重点: 代码建议、潜在问题、最佳实践      │
└──────┬───────────────────────────────────┘
       ↓
┌──────────────────────────────────────────┐
│  ✅ CI/CD 检查                            │
│  触发: PR 创建/更新                      │
│  时间: ~10-20 分钟                       │
│  检查: 编译、测试、覆盖率、架构合规       │
└──────┬───────────────────────────────────┘
       ↓
┌──────────────────────────────────────────┐
│  👤 第三阶段: 人工审查（CODEOWNERS）     │
│  触发: AI 审查 + CI 通过后               │
│  时间: 根据 PR 复杂度                    │
│  重点: 业务逻辑、设计决策、代码风格       │
└──────┬───────────────────────────────────┘
       ↓
┌─────────────┐
│  合并到 master  │
└─────────────┘
```

## 🤖 第一阶段: Claude Code 自动初审

### 职责范围

Claude Code 负责全面的代码质量检查，是第一道防线。

### 审查重点

#### 1. 架构合规性（🔴 严重问题）

**检查项**:
- ✅ 严格遵守 **Record-Only 系统约束**（仅 CRUD + 历史查询）
- ❌ **禁止使用**:
  - Docker, Kubernetes
  - Redis
  - CQRS, MediatR
  - Event-Driven Architecture
  - 微服务架构
  - GraphQL, gRPC
  - 消息队列（RabbitMQ/Kafka）
- ✅ 符合 `.ai/rules.json` 和 `_governance/architecture.md` 定义的技术标准

**处理方式**:
- 🔴 发现违规 → 立即标注，PR 必须修复后才能继续

#### 2. C# / .NET 8 最佳实践（🟡 建议问题）

**检查项**:
- 命名规范:
  - `PascalCase` - 类型、公开成员
  - `_camelCase` - 私有字段
  - `UPPER_SNAKE_CASE` - 常量
- 异步约定:
  - 涉及 I/O 必须 `async/await`
  - 异步方法名以 `Async` 结尾
- 依赖注入:
  - 仅使用构造函数注入
  - 禁止 `ServiceLocator` 或 `Container.Resolve()`
- 资源管理:
  - 正确使用 `IDisposable` 和 `using`
- Nullable 引用类型:
  - 正确处理可空性注解

#### 3. WPF / Prism MVVM 规范（🟡 建议问题）

**检查项**:
- ViewModel:
  - 必须继承 `BindableBase` 或实现 `INotifyPropertyChanged`
- 导航:
  - 使用 Prism `IRegionManager`
  - 禁止直接 `new Window()`
- 对话框:
  - 使用 Prism `IDialogService`
  - 禁止 `MessageBox.Show()`
- 事件聚合:
  - 使用 `IEventAggregator`
- 命令:
  - 使用 `DelegateCommand` 或 `DelegateCommand<T>`

#### 4. 代码质量（🟢 优化建议）

**检查项**:
- 单个文件 ≤500 行
- 方法圈复杂度 ≤10
- 避免重复代码（DRY 原则）
- 清晰的注释（复杂逻辑必须注释）
- 魔法数字提取为常量

#### 5. 安全性（🔴 严重问题）

**检查项**:
- SQL 注入防护（参数化查询）
- 敏感信息不得硬编码
- 输入验证与清理
- 正确的异常处理（不泄露堆栈信息）

#### 6. 性能（🟡 建议问题）

**检查项**:
- 避免 N+1 查询（EF Core）
- 合理使用缓存（`IMemoryCache`）
- 大集合操作使用 LINQ 延迟执行
- WPF UI 操作在 UI 线程，耗时操作异步化

#### 7. 测试覆盖（🟡 建议问题）

**检查项**:
- 核心逻辑必须有单元测试
- 测试命名清晰（Given_When_Then 模式）
- 边界条件与异常场景测试

#### 8. 文档同步（🟡 建议问题）

**检查项**:
- 架构变更需更新 `docs/architecture/` 文档
- API 变更需更新 `docs/api/` 文档
- 新增功能需更新模块 README

### 审查输出格式

```markdown
## 🤖 Claude Code Review 报告

### 🔴 严重问题（必须修复）
- [问题描述] 位置：`文件名:行号`

### 🟡 建议问题（建议修复）
- [问题描述] 位置：`文件名:行号`

### 🟢 优化建议（可选）
- [建议描述]

### ✅ 良好实践
- [表扬项目]
```

### 开发者响应

1. **🔴 严重问题**: 必须修复后才能继续
2. **🟡 建议问题**: 评估是否修复，可以在 PR 评论中说明原因
3. **🟢 优化建议**: 可选修复，或创建后续 Issue

## 🤖 第二阶段: GitHub Copilot 二审

### 职责范围

Copilot 提供补充性建议，关注代码改进机会和潜在问题。

### 审查重点

#### 1. 代码改进建议

**检查项**:
- 更简洁的代码写法
- 更高效的算法实现
- 更清晰的命名

#### 2. 潜在问题检测

**检查项**:
- 未处理的边界条件
- 可能的空引用异常
- 性能瓶颈

#### 3. 最佳实践建议

**检查项**:
- .NET 8 新特性使用
- LINQ 优化
- 异步编程改进

### 审查输出格式

Copilot 通过 PR 评论提供内联建议：

```
💡 Copilot 建议:
可以使用 C# 12 的新特性简化这段代码：
[建议代码]
```

### 开发者响应

1. 评估建议的价值
2. 采纳或说明不采纳的原因
3. 可以在后续 Issue 中跟进

## 👤 第三阶段: 人工审查（CODEOWNERS）

### 职责范围

人工审查是最后一道防线，关注 AI 无法判断的领域。

### 审查重点

#### 1. 业务逻辑正确性（🔴 核心重点）

**检查项**:
- 实现是否符合业务需求
- 边界条件处理是否完整
- 异常场景是否考虑周全

#### 2. 设计决策合理性（🟡 重要）

**检查项**:
- 架构选择是否合理
- 扩展性是否良好
- 是否过度设计或设计不足

#### 3. 代码可读性与可维护性（🟢 优化）

**检查项**:
- 变量/方法命名是否清晰
- 注释是否充分
- 代码结构是否合理

#### 4. 团队协作与知识传播（🟢 优化）

**检查项**:
- 是否有值得学习的模式
- 是否需要团队分享
- 是否需要文档说明

### 审查清单

人工审查者应逐项检查：

- [ ] 业务逻辑正确
- [ ] 符合项目架构标准（Record-Only 系统）
- [ ] 命名规范清晰
- [ ] 注释充分
- [ ] 测试覆盖充分
- [ ] 文档已同步更新
- [ ] AI 审查反馈已处理

### 审查输出格式

```markdown
## 👤 人工审查反馈

### 必须修复
- [问题描述]

### 建议改进
- [建议描述]

### 审批决定
- [ ] ✅ 批准合并
- [ ] 🔄 需要修改后重新审查
- [ ] ❌ 拒绝（说明原因）
```

## ✅ 最佳实践

### 对于开发者

1. **提交 PR 前**:
   - 本地编译通过
   - 本地测试通过
   - 自查是否符合代码规范

2. **收到 AI 审查反馈后**:
   - 优先修复 🔴 严重问题
   - 评估 🟡 建议问题
   - 考虑 🟢 优化建议
   - 在 PR 评论中说明处理情况

3. **请求人工审查时**:
   - 确保 AI 审查通过
   - 确保 CI 检查通过
   - 在 PR 描述中说明关键变更

### 对于审查者

1. **审查准备**:
   - 阅读 PR 描述和关联 Issue
   - 查看 AI 审查反馈
   - 查看 CI 检查结果

2. **审查过程**:
   - 关注业务逻辑正确性
   - 关注设计决策合理性
   - 不要重复 AI 已发现的问题

3. **审查反馈**:
   - 明确标注严重程度
   - 提供具体改进建议
   - 如有疑问，与开发者讨论

## 📝 FAQ

### Q1: AI 审查可以完全替代人工审查吗？

**A**: 不可以。AI 审查擅长发现代码质量、规范、安全等技术问题，但无法判断业务逻辑正确性和设计决策合理性。人工审查仍然是必不可少的。

### Q2: 如果 AI 审查给出了错误的建议怎么办？

**A**: 可以在 PR 评论中说明原因，标注 `@claude` 或 `@copilot` 并解释为什么不采纳该建议。人工审查者会最终决定。

### Q3: Copilot 审查和 Claude Code 审查有什么区别？

**A**:
- **Claude Code**: 全面的代码质量检查，关注架构合规、安全性、最佳实践
- **Copilot**: 补充性建议，关注代码改进机会、简洁性、.NET 新特性使用

### Q4: 人工审查需要多长时间？

**A**: 取决于 PR 复杂度：
- 简单 PR（<100 行）: 5-15 分钟
- 中等 PR（100-500 行）: 30-60 分钟
- 复杂 PR（>500 行）: 1-3 小时（建议拆分）

### Q5: 可以跳过 AI 审查直接人工审查吗？

**A**: 不可以。AI 审查是自动触发的，且分支保护规则强制要求通过。这可以减少人工审查负担，提高效率。
