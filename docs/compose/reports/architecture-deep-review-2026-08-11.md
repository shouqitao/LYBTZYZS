## 一、架构愿景与演化（9.0）

### 1.1 决策轨迹（17 ADR 还原）
```
0001 聚合根 → 0002/0009 双模式 → 0003 测试 → 0004 用户上下文 → 0005 超管
→ 0006 组件 → 0007 VM 组合 → 0008 令牌 → 0010 本地统一服务层 → 0011 Mapperly
→ 0012 MVVM 工具包 → 0013 SignalR → 0014 配置双模式 → 0015 API 版本化
→ 0017 模块化 CQRS → 0018 领域事件
```

**评测**：这是一条**收敛主导**的轨迹——从「多方案并存」（双轨、门面、手写映射）逐步单轨化。ADR-0010/0011/0014/0017 是收敛类决策（统一服务层/Mapperly/配置/模块化），ADR-0008/0013/0018 是能力类决策。**罕见地**：决策有「待实施项」清单（ADR-0014 明确标注）——没有「决策即完成」的假象。A-16~A-31 批次把 ADR 落地为代码 + 架构守卫，闭环质量高。

**扣分点**：ADR-0016 缺失（编号空洞——影响可追溯完整性）；ADR 无「被否决选项」的记录深度（部分决策只有结论无备选对比）。

### 1.2 规模合理性
39,619 行 / 29 源项目——**项目数量偏多**（小团队维护 29 个 csproj 的编译开销/引用管理成本高），但分层粒度清晰（Shared 5 / Server 8 / Desktop 16 / Tools 1）。这是「模块自治」的代价——可接受，但**项目合并的评估应持续进行**（A-31-C3 已合并 4 模块——趋势正确）。

## 二、分层与依赖（9.2）

### 2.1 依赖方向（架构测试实证）
```
Shared ← Server.Infrastructure ← Server.Modules ← Server.WebAPI
                                      ↖ Desktop（LocalWebAPI 复用 Server 服务层）
Desktop.Contracts ← Desktop.Foundation ← Desktop.Modules ← Shell
```

- **3-Layer 纪律**：Controller→Service→Repository→DbContext 单向——87 条守卫含 0 越层/0 环/模块 0 直接引用（A-16 实证）——**依赖方向由测试强制，非口头约定**——这是本系统最强的一点。
- **双轨共享**：LocalWebAPI 复用 Server 服务层（ADR-0010）——远程/本地双端**同一业务逻辑**——避免双份维护（行业常见坑，这里做对了）。
- **跨模块接口（P08）**：模块互不引用 + 域接口（IXxxCrossModuleService）——A-31-C8 删除统一门面是**正确方向**（门面双轨是反模式）。

**扣分点**：
- Desktop 16 项目中有「模块」与「角色」（Roles/Admin、Roles/Clinical）两层抽象——Roles 层与 Modules 层的边界语义偶有重叠（如 Sysadmin 模块在 Roles/LYBT.Desktop.Admin 下——命名与 Modules 不一致）。
- Shell 项目承载过多（App 启动/登录协调/事件/配置/服务注册——~20 类）——有「上帝项目」苗头，但当前规模可承受。

### 2.2 聚合根边界（ADR-0001）
MedicalCase 唯一聚合根 + Registration/Patient 跨聚合仅 ID 引用——**DDD 教科书级**。挂号→接诊→辨证→处方→收费→打印全挂医案生命周期——事务边界清晰。QuickVisit 原子创建挂号+医案（REG-002）验证了「聚合根事务」语义——设计一致性高。

## 三、核心设计决策评估（8.6）

### 3.1 双模式（Remote/LocalWebAPI）——✅ 合理
嵌入式 Kestrel（LocalWebAPI）+ Refit HTTP（Remote）双端——**URL 驱动切换**（ADR-0009）+ 手动切换守卫（SHELL-007 阻断未完成医案跨模式）。数据孤立 N1 是**需求层决策**（小诊所离线场景）——架构上诚实（不做虚假同步）。

**风险**：双端 Controller 树同步是持续维护成本（每次端点变更双改）——架构测试 LocalWebApiPatternTests 守护了签名一致性——**缓解到位**。

### 3.2 RefreshToken=access（T4 决策）——✅ 可辩护
服务端会话哈希 + 轮换 + 重放检测——语义等价独立 refresh 链。**适合威胁模型 G-02**（小诊所、无高价值凭据市场）。缺点：无 refresh 令牌的「离线可签发」能力（无状态刷新）——但系统已有 AutoLogin（30 天）覆盖离线场景——决策组合自洽。

### 3.3 配置中心（SHELL-018）——✅ 分层生效设计
热更新层（功能开关/诊所信息）+ 重启层（会话/连接/安全）+ 原子写（runtime-overrides/client-store）+ 白名单/脱敏/审计/限频——**运维闭环完整**（sysadmin 全远程）。JsonFileConfigurationStore 的「覆盖文件而非改写源文件」设计（可回滚）优于常见的直接改写。

### 3.4 权限体系 ——✅ 5 策略精细
DoctorOnly/AdminBusinessOnly/AdminOrSuperAdmin/SysAdminOnly/DoctorOrAdmin + 端点级守卫 + 部署 SysAdminOnly 收紧（DEPLOY-PERM）——**职责分离清晰**（Admin 业务、SysAdmin 运维）。

### 3.5 商榷点（非缺陷）
| 决策 | 商榷 | 当前判断 |
|------|------|---------|
| 读卡器固件接口缺失 | 诊断「驱动未暴露」是诚实但功能不完整 | 可接受（硬件厂商限制） |
| 异常体系 6 类（App/Business/NotFound/Conflict/Unauthorized/Api/Validation） | 类数量偏多——部分可用 ErrorCode 表达 | 可接受（映射清晰） |
| 报表双轨复刻（A-30 发现） | 远程/本地报表实现策略分歧 | 已记录——后续收敛候选 |

## 四、代码质量与一致性（8.8）

### 4.1 收敛成果（实证）
- **技术栈减法**（A-27）：BCrypt→Identity PBKDF2、删 Swagger 半成品、Sqlite 移除——依赖最小化
- **映射统一**：Mapperly 唯一（A-31-C8）——手写映射 0
- **异常/日志集中**（A-31-C1/C2/ERR-006/007）：单一定义 + 自动映射
- **模块合并**（A-31-C3a/C3b）：Auth+Users→Identity、Herbs+Formula→Catalog
- **命名收敛**（Q-03）：命名空间复数统一 + 类型命名一致

### 4.2 编码卫生
0 警告门禁（`--no-incremental` 全量）+ 中文注释统一 + 每批 commit 带门禁证据——**工程纪律在 39,619 行中可见**（无明显「应删未删」——O1 死代码清理 + C6/C7 持续清理）。

**扣分点**：
- Desktop 部分 XAML 重复模式（MasterDetail 模板复制——T1 发现）——已由基类化（D3/T3-1）缓解但未全消
- 手写 fake 仓储（测试零 mock 约定）——无框架的 fake 可维护性一般（接口变化时同步改）

## 五、测试策略（8.5）

| 层 | 数量 | 守护 |
|----|------|------|
| 架构测试 | 87 | 分层/依赖/模式/聚合根/本地模式——**机器强制的架构纪律** |
| Server 单测 | 618+ | 业务逻辑主体（实体/服务/handler/仓储/配置） |
| Desktop 单测 | ~200 | VM/服务/工具——纯内存（T2 去 DB 耦合） |
| Desktop 集成 | ~150 | E2E（LocalDB/localhost 依赖——P0-06 环境类） |
| AC 映射 | 147 US | 需求 AC→测试守护（P0 全闭环 15 用例 + 近批 12 + 结构 22） |

**评测**：T1 教训（测试自洽不对照需求）→ AC 映射 → P0-TEST → P23——**测试从「自证」走向「守护需求」的转变是本系统最值得称道的演进**。Server 620 测试零 mock（真实依赖 + EF InMemory）——集成度高的单测。

**扣分点**：
- 集成测试环境依赖（LocalDB/localhost）——CI 无法全绿——**最大测试短板**（需容器化 LocalDB 或抽离）
- 无 Property-based/模糊测试（配置解析/日期边界可受益）
- 无 E2E UI 自动化（WPF 层靠手动验收）

## 六、安全设计（8.9）

| 面 | 实现 | 评测 |
|----|------|------|
| 认证 | JWT + refresh 轮换 + AutoLogin 30 天 + 本地验签 | ✅ P0 全闭环（15 测试用例） |
| 权限 | 5 策略 + 端点守卫 + 部署 SysAdminOnly | ✅ 职责分离（DEPLOY-PERM 收紧） |
| 会话 | 改密/重置撤销 + 重放检测 | ✅ RevokeAll 测试 |
| 审计 | SecurityAuditService 全记录 + SensitiveData 脱敏 | ✅ 审计测试 + JSON 脱敏转换器 |
| 限流 | 登录限流 + 配置重启限频 | ✅ 滑动窗口 |
| 配置安全 | 白名单/黑名单 + 脱敏掩码 + SysAdminOnly | ✅ WritePolicy 22 用例 |

**评测**：威胁模型意识强（G-02 小诊所场景明确）——**没有过度设计**（无 OAuth 复杂链、无分布式锁）——「正确的安全量级」比「最多的安全特性」更难，本系统做到了。

## 七、风险与演化能力

### 7.1 当前风险（已记录边界）
| 风险 | 等级 | 缓解 |
|------|:---:|------|
| 集成测试环境依赖 | 中 | 单元层守护主体；容器化可解 |
| 双端 Controller 同步成本 | 中 | LocalWebApiPatternTests 签名守护 |
| 项目数偏多（29） | 低 | 持续合并评估（趋势正确） |
| Shell 上帝项目苗头 | 低 | 当前规模可承受 |

### 7.2 演化建议（3 项高价值）
1. **集成测试容器化**（LocalDB 入 CI）——消除 P0-06，测试全绿闭环
2. **「域门面」演进为「跨模块查询服务」**——IXxxCrossModuleService 若继续膨胀，考虑按查询语义拆分（读聚合服务）
3. **Shell 拆分**（启动协调/登录协调/事件/配置）——按职责拆 3-4 个服务类，防上帝项目固化

## 八、最终评测

**结论**：LYBTZYZS 在 39,619 行规模上展现了**行业罕见的架构纪律**——87 条机器强制的架构守卫、17 份可追溯的 ADR、从「测试自洽」到「测试守护需求」的自觉演进、收敛主导的技术栈。**这不是「原型长成的系统」，而是「被持续治理的系统」**。

**主要扣分**：集成测试环境依赖（最短板）、项目数偏多、Shell 职责集中——均为「演化期」问题而非「当前态」缺陷。

**评分：8.8/10**——在当前规模与业务复杂度下，架构决策质量高、执行纪律强；建议聚焦集成测试容器化 + 持续合并评估，保持「收敛优先」节奏。
