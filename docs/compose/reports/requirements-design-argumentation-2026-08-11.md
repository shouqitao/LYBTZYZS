## 一、需求分析专家视角：需求理解论证

### 1.1 领域模型还原（R 专家）

系统需求还原为 4 角色 × 5 核心流程：

```
角色边界（UserRole 语义）：
  Receptionist 前台 —— 患者建档/挂号/取消（US-PAT-001~004、US-REG-001/004）
  Doctor 医生       —— 接诊/辨证/处方/收费/打印（US-MC-001~020、US-PRINT-*）
  Admin 管理员      —— 业务管理（用户/药材/验方/报表），不能管 Admin
  SuperAdmin 系统管理员 —— 全部 + 系统运维（SHELL-013/017/018/019）

核心旅程：
  建档(前台) → 挂号(前台) → 接诊(医生) → 辨证(MC-002) → 处方(MC-003)
  → 收费(MC-015) → 打印(PRINT) → 完成(MC-010) → 历史追溯(MC-008/009)
```

**聚合根判断（R 专家认可）**：MedicalCase 为唯一聚合根（ADR-0001）——「一医案一诊断，一医案至多一处方」——辨证/处方/收费/打印全部围绕医案生命周期——符合小诊所「一次看诊一条链」的业务本质。挂号（Registration）与患者（Patient）为跨聚合引用（仅 ID）——DDD 边界清晰。

**R 专家结论**：需求理解度高——领域模型还原准确（聚合根/角色边界/旅程语义与业务一致）；需求覆盖完整（139/147 达成，剩余 3⚠️+1🔴+4🧲 均为明确边界：CARD-002 用户搁置、SHELL-003 代码待对齐、规划项）。

### 1.3 需求语义的深度理解（R 专家亮点）

- **QuickVisit 双重职能**（REG-002 定位补注）：远程=急诊通道、本地=无前台常规入口——需求文档明确标注，避免「死代码」误解
- **双模式分野**（11-business-flows）：本地=远程功能完整副本（数据孤立 N1），差异由用户配置调节——理解「小诊所离线看诊」业务本质
- **配置热更新边界**（SHELL-018 决策 A）：功能开关/诊所信息热更新、其余重启——区分「即时生效」与「需重启」两类配置语义

## 三、双角色对话（交叉质询）

**R 质疑 1：MedicalCase 唯一聚合根是否过度设计？** 挂号→医案链路中，挂号状态（Waiting/InProgress）与医案状态（Active/Completed）双状态机——为何不把 Registration 也当聚合根？

**D 回应**：Registration 是**前台的临时登记**（队列语义），接诊（StartVisit）即创建 MedicalCase 聚合——医案才是诊疗数据的完整载体（辨证/处方/收费/打印全挂其下）。双状态机是**流程阶段**而非**数据聚合**——Registration 状态仅 4 态（队列管理），MedicalCase 状态是业务核心（10+ 流转守卫）。拆分聚合根会撕裂「一医案一条链」的事务边界（QuickVisit 原子创建挂号+医案正是证据——见 REG-002）。

**R 质疑 2：双模式的数据一致性？** 本地（LocalDB）与远程（SQL Server）数据如何统一？离线期间远程产生的新数据？

**D 回应**：**数据孤立 N1 是明确设计**（11-business-flows）——本地模式=独立数据岛，不做同步（小诊所场景：外出看诊带回纸质/手工补录，或本地模式作为主模式长期使用）。切换守卫（SHELL-007）阻断「本地有未完成医案时切远程」——防止跨库操作。这是**需求层决策**（用户确认），非设计疏漏。

**R 质疑 3：RefreshToken=access token 的凭据设计？** 不引入独立 refresh 令牌是否削弱安全性？

**D 回应**：服务端按**会话哈希**校验 + 每次刷新**轮换**（旧令牌即时作废）+ 重放检测（登出后旧令牌拒绝）——安全语义等价于独立 refresh 链（旋转 + 服务端状态），但**零额外令牌链复杂度**（T4 决策——最小实现，符合小诊所威胁模型 G-02）。P0-TEST 5 用例守护（签发/旋转/身份保留/非法拒绝）。

**R 质疑 4：配置中心「重启生效」体验？** 医生改配置要重启整个 Desktop？

**D 回应**：分层生效——**热更新层**（功能开关/诊所信息即时生效）覆盖高频调整；**重启层**（会话/连接/安全）为低频变更。本地模式重启**仅重启内嵌 LocalWebAPI**（决策 B——Desktop 会话不丢）；远程模式走 API 延迟重启（30 秒 + 限频 + 二次确认）。这是「体验」与「配置正确加载时机」的平衡——重启语义经用户确认。

**R 质疑 5：测试环境依赖（LocalDB/localhost）？** 大量 Integration 测试本机失败——测试体系可信吗？

**D 回应**：**可信且有明确边界**——T2 已解除 148 个纯 VM 测试的 DB 耦合（纯内存基类）；Integration 测试（146 个连 localhost:5000）是**环境依赖类**（P0-06 已知）——其失败非回归（stash 基线实证）。单元层（Server 620 + Desktop 相关）全绿守护业务逻辑；Integration 用于端到端验收（需环境）。AC-TEST 映射已把守护强度分层记录（单元层=守护主体）。

**R 总结陈词**：需求理解完整（147 US 覆盖 + 领域模型准确 + 边界清晰），方案在「正确性优先」与「小诊所复杂度控制」间找到了务实平衡——没有为理论纯度过度设计。

**D 总结陈词**：方案完整性经四层论证（架构/功能/安全/测试）无空白；合理性经五轮质询（聚合根/双模式/凭据/重启/测试）全部站得住；剩余风险均为**已记录的边界决策**而非设计缺陷。

## 四、结论

### 4.1 需求理解度：高（论证成立）
- 领域模型还原准确（聚合根/角色边界/旅程语义与业务一致）
- 需求语义深度理解（QuickVisit 双职能/双模式分野/热更新边界）
- 覆盖完整（139/147 ✅，剩余为明确边界决策）

### 4.2 方案完整性：无空白（四层论证）
- 架构层：3-Layer + CQRS + 模块自治 + 双模式（87 架构守卫）
- 功能层：15 域全落地（近批 B1/B2/SHELL-018/019 补齐 backlog）
- 安全层：认证/权限/会话/审计/限流五面闭环（P0 全修复 + 测试守护）
- 测试层：单元守护主体 + Integration 环境依赖明确分层

### 4.3 剩余风险（已记录边界，非缺陷）
| 风险 | 性质 |
|------|------|
| CARD-002 降级链 | 用户搁置（UI 设计时整体考虑） |
| SHELL-003 LoginCoordinator 旁路 | 代码待对齐（C1 遗留——🔴 唯一） |
| 本地/远程数据孤立 N1 | 需求层决策（不做同步） |
| Integration 环境依赖 | P0-06 已知（单元层守护主体） |
| 读卡器固件接口 | 驱动未暴露（诊断如实提示） |

**最终结论**：系统对需求的理解准确且深入；方案设计完整（无空白层）、合理（关键决策经质询成立）；剩余缺口为显式边界决策——当前系统状态与「需求文档所描述的系统」高度一致（traceability 139/147 ✅ 实证）。
