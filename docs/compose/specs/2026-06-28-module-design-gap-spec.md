# 模块级设计文档补全规格

> **日期**: 2026-06-28
> **状态**: 待审
> **范围**: 为 10 个 v1.0 模块补全模块级设计文档

## [S1] 问题

当前文档体系覆盖了架构级（37文件）和需求级（18文件），但每个业务模块缺少独立的「模块设计文档」。这意味着开发者需要同时阅读多个文档才能理解单个模块的设计意图。

## [S2] 目标

为每个 v1.0 模块创建独立设计文档，格式统一，包含以下标准章节：

| 章节 | 内容 | 必填 |
|------|------|:---:|
| 模块概述 | 职责、边界、依赖 | 是 |
| 接口契约 | 服务接口、DTO、API 端点映射 | 是 |
| 状态机 | 状态转换图（如有） | 条件 |
| 数据流 | 跨模块调用链、时序图 | 是 |
| 异常处理 | 模块特有异常模式 | 是 |
| 业务规则 | 关键约束、验证规则、与需求 US 映射 | 是 |
| 模块交互 | 与其他模块的依赖和通信 | 是 |

## [S3] 模块优先级与范围

**P0（核心，先做）**:
- MedicalCase（19 US）— 核心聚合根，CQRS，状态机
- Registration（8 US）— 双模式工作流 + SignalR + QuickVisit
- Auth（13 US）— Token 安全 + 多角色 + 本地简化认证

**P1（重要）**:
- Patients（13 US）— 拼音搜索 + 读卡器 + 敏感数据
- Herbs（13 US）— 引用检查 + Excel 导入
- Formulas（13 US）— 验证状态机 + 延迟绑定

**P2（标准）**:
- Users（12 US）— 四级权限 + 批量操作
- Printing（4 US）— 双引擎渲染（已有部分文档）
- Reports（3 US）— 聚合查询

**P3（已有覆盖）**:
- Platform（43 US）— Shell/Config/Error/Logging/Health/CardReader 已有详细文档

## [S4] 文档模板结构

```markdown
# [模块名] 模块设计

## 模块概述
- 职责边界
- 依赖关系（上下游模块）
- 关键 US 清单

## 接口契约
- Service 接口定义
- DTO 结构
- API 端点映射表

## 状态机（如有）
- 状态定义
- 转换规则
- 边界条件

## 数据流
- 请求处理时序图
- 跨模块调用链
- 数据访问模式（Repository/Service）

## 异常处理
- 模块特有异常类型
- 错误码映射
- 异常传播路径

## 业务规则
- 关键约束
- 验证规则
- 与需求 US 的追溯映射

## 模块交互
- 依赖的其他模块
- 被依赖关系
- 通信方式（接口/事件）
```

## [S5] 实施计划

| 批次 | 模块 | 估算工作量 |
|------|------|:---:|
| 1 | MedicalCase（核心聚合根） | 高 |
| 2 | Registration + Auth（双模式+安全） | 高 |
| 3 | Patients + Herbs + Formulas（业务模块） | 中 |
| 4 | Users + Printing + Reports（标准模块） | 低 |

## [S6] 验收标准

每个模块设计文档完成后：
1. 接口契约与 `04-api-reference/` 端点一致
2. 状态机与 `07-medical-cases.md` 需求一致
3. 业务规则与 `02-requirements/` US 映射完整
4. 异常处理与 `06-error-handling.md` 规范一致
