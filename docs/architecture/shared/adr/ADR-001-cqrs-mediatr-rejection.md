# 架构决策报告：不引入完整CQRS及MediatR模式

**报告编号**: ADR-001  
**报告日期**: 2025年9月24日  
**作者**: Gemini (AI Assistant)  
**状态**: 建议

---

## 1. 背景与目的

近期，团队讨论了引入完整CQRS（命令查询责任分离）模式及MediatR库的可能性，以期优化项目架构。本报告旨在基于项目当前的实际规模、业务复杂度及现有架构，对这两项技术的必要性进行分析，并提供正式的架构决策建议。

## 2. 项目现状分析

在决策前，我们对项目现状进行了全面评估，关键信息如下：

*   **项目规模**：
    *   **目标用户**：小型中医诊所（2-20人）。
    *   **核心用户**：2-5名医生，并发用户数设计目标为 **< 10人**。
    *   **数据体量**：日处理患者 **< 100人**，预计5年数据量 **< 10GB**。
    *   **结论**：项目属于小规模、低并发、中低数据量的应用。

*   **现有架构**：
    *   项目已在后端实现了**轻量级的读写分离**。
    *   **查询链路**：`Controller → QueryService → ReadRepository`，此链路已包含独立的缓存策略和性能优化。
    *   **写入链路**：遵循传统的 `Controller → BusinessService → DbContext/WriteRepository` 模式。
    *   **结论**：架构清晰，且已采纳了CQRS的核心思想精髓，实现了关注点分离。

*   **性能表现**：
    *   根据文档，现有查询层在缓存支持下性能表现优异（API响应 < 200ms，缓存命中率 > 80%），已完全满足当前及可预见未来的性能需求。

*   **项目指导思想**：
    *   项目文档明确指出，核心价值观是“**稳定优先**”、“**最小变更**”，推崇清晰、可预测、易于维护的架构。

## 3. 技术选型分析

### 3.1. 完整CQRS模式分析

完整的CQRS模式通常意味着为读和写操作建立不同的数据模型，甚至独立的数据库。

**不引入的理由**:

1.  **性能冗余，过度设计**：
    完整的CQRS主要解决的是高并发系统中的读写性能瓶颈。对于本项目的小规模应用场景，这是一个典型的“过度设计”。当前的`ReadRepository`模式已足够应对性能挑战。

2.  **不必要的复杂性**：
    引入独立的读写模型会带来数据同步（最终一致性）、模型维护、代码量增加等一系列问题，显著提高了系统的复杂度和维护成本。这与项目“稳定优先”的原则相悖。

### 3.2. MediatR库分析

MediatR是一个进程内的消息分发器，通过请求/处理器模式解耦组件。

**不引入的理由**:

1.  **增加代码的间接性和追踪难度**：
    MediatR的核心优势是解耦，但代价是增加了代码的“间接性”。开发者无法通过简单的“Go to Definition”追踪代码执行流，必须去寻找对应的`Handler`，这降低了代码的直观性和可调试性，对于新成员上手不友好。

2.  **引入不必要的样板代码**：
    为每一个业务操作创建`Command/Query`和`Handler`类，对于本项目中大量直接的CRUD操作而言，会显得非常繁琐，增加了不必要的代码量。

3.  **现有方案已足够清晰**：
    对于写操作，一个职责清晰、逻辑内聚的`BusinessService`（业务服务层）是比引入MediatR更简单、更直接的解决方案。它同样能实现业务逻辑的封装，且没有增加额外的学习成本和架构复杂度。

## 4. 结论与建议

**核心结论**：
在凌隐宝堂中医诊所管理系统的当前阶段，引入完整的CQRS模式和MediatR库**均没有必要**。这两种技术所解决的核心痛点（高并发性能、极端复杂的业务解耦）在本项目中并不突出。强行引入将导致过度设计，违背项目“稳定优先、最小变更”的核心原则。

**推荐的架构策略**：

1.  **坚持并优化现有模式**：继续沿用并完善当前行之有效的轻量级读写分离架构。`QueryService` + `ReadRepository`的查询模式是本项目的最佳实践。
2.  **强化标准服务层**：对于写入操作，继续使用标准、清晰的服务层（Service Layer）来封装业务逻辑。确保服务职责单一、接口明确。
3.  **保持架构的简洁与直观**：避免引入不必要的抽象和间接层，让代码的流转路径尽可能清晰、易于追踪，以降低维护成本。

此决策可在未来项目规模或业务复杂度发生10倍以上的量级增长时，再重新进行评估。
