# 技术路线建议报告 (Technology Roadmap Suggestion Report)

**报告编号**: ADR-002  
**报告日期**: 2025年9月24日  
**作者**: Gemini (AI Assistant)  
**状态**: 建议

---

## 1. 核心原则与目标

为杜绝“为了技术而技术”的问题，并确保所有技术决策都服务于项目的长远健康，本技术路线严格遵循以下核心原则：

*   **稳定性压倒一切 (Stability First)**：技术选型优先选择成熟、稳定、具有长期支持（LTS）的方案。避免追逐潮流，不把生产环境作为新技术的试验场。
*   **务实主义与简约化 (Pragmatism & Simplicity)**：始终选择能够解决当前问题的、最简单的方案。当简单的方案（如标准分层架构）能满足需求时，绝不引入不必要的复杂设计（如完整的CQRS/MediatR）。
*   **发挥存量优势 (Leverage Existing Strengths)**：项目的技术栈（.NET/WPF/EF Core）是成熟且强大的组合。我们应深化对现有技术的投资，而不是将精力分散到新的技术领域，以实现最高的投资回报率。
*   **问题驱动，而非技术驱动 (Problem-Driven, Not Technology-Driven)**：任何技术或工具的引入，都必须是为了解决一个已知的、具体的问题（如性能瓶颈、开发效率低下、代码质量问题），并需论证其收益大于成本。

本报告的目标是基于以上原则，为项目“锁定”未来1-2年的技术栈，统一团队认知，并指明后续的重构与优化方向。

## 2. 技术栈锁定决策

### 2.1. 后端 (Backend)

| 领域 | 决策 | 理由 |
| :--- | :--- | :--- |
| **运行时** | **锁定 .NET 8 LTS**。后续仅考虑向未来的LTS版本（如 .NET 10）升级。 | .NET 8 提供长期支持，保证了稳定性和安全性。跳过非LTS版本可以避免不必要的迁移成本和潜在的不稳定性。 |
| **Web框架** | **锁定 ASP.NET Core**。 | 这是.NET生态的官方标准，性能卓越，社区成熟，团队已有丰富的实践经验。 |
| **数据访问** | **锁定“EF Core + Dapper/优化SQL”的混合模式**。 | 这种模式已被项目验证为行之有效：**写操作**使用EF Core，享受其强大的对象映射和迁移功能，提升开发效率；**读操作**沿用`ReadRepository`模式，内部可按需使用Dapper或EF Core的`AsNoTracking()`等原生SQL优化手段，保证极致性能。 |
| **数据库** | **锁定 SQL Server**。 | 项目已基于SQL Server构建，其功能强大、生态成熟。在当前数据量和并发规模下，没有更换数据库的必要。 |

### 2.2. 前端 (Frontend)

| 领域 | 决策 | 理由 |
| :--- | :--- | :--- |
| **UI框架** | **锁定 WPF + Prism 8.x**。**明确不考虑**向MAUI、Blazor等其他UI框架迁移。 | 项目当前最紧迫的任务是**修复和稳定**现有的WPF客户端。任何UI框架的迁移都是一项巨大、高风险的工程，违背了“稳定优先”的原则。我们应将全部精力投入到让现有WPF应用变得健壮、可维护。 |
| **UI组件库** | **锁定原生WPF控件，暂不引入第三方UI组件库**。 | 在系统完全稳定之前，应优先使用原生控件确保核心功能的健壮与可用。这避免了引入新依赖带来的学习成本和集成风险。UI的现代化和美化工作，应作为“稳定化阶段”之后独立规划的任务。 |
| **客户端-服务端通信** | **锁定 Refit**。 | Refit 提供了类型安全的HTTP客户端，能将API定义转化为C#接口，显著减少了手写HTTP请求的错误，提升了开发体验。 |

### 2.3. 测试 (Testing)

| 领域 | 决策 | 理由 |
| :--- | :--- | :--- |
| **测试框架** | **锁定 xUnit** 作为主要测试框架。 | xUnit是.NET社区现代且主流的选择，其设计哲学（如独立的测试实例）有助于编写更可靠、无副作用的测试。 |
| **辅助工具** | **锁定 Moq (或 NSubstitute) + FluentAssertions**。 | 这是测试的“黄金搭档”。Moq用于创建模拟对象，FluentAssertions则提供了可读性极强的断言语法，能显著提升测试代码的质量和可维护性。 |

## 3. 路线图与关键举措

基于以上技术栈决策，我们建议后续的开发/重构工作按以下三个阶段推进：

### Phase 1: 稳定化阶段 (Stabilization - 立即执行)

此阶段的目标是让项目恢复“健康”状态，为后续所有工作奠定基础。
1.  **修复服务端测试**：确保所有服务器端单元/集成测试100%通过。
2.  **修复桌面端编译**：解决所有编译错误，确保客户端可以稳定运行和调试。
3.  **建立桌面端测试基线**：为ViewModel和核心服务创建单元测试，实现从0到1的突破。

### Phase 2: 核心重构阶段 (Core Refactoring - 短期)

此阶段专注于提升内部代码质量和一致性。
1.  **深化后端服务层重构**：遵循“单一职责”原则，对臃肿的服务进行拆分；引入`FluentValidation`统一验证逻辑。
2.  **完成桌面端ViewModel重构**：全面推广使用`ModernManagementViewModel`等现代化基类，统一界面交互逻辑。
3.  **统一UI资源与清理**：将所有零散的转换器（Converters）、样式（Styles）集中到`UnifiedDesignSystem.xaml`，为未来可能的UI升级做好准备。

### Phase 3: 优化与展望阶段 (Optimization & Outlook - 中期)

此阶段关注于长期的健康度和开发者体验。
1.  **全面清理技术债**：根据积压的待办事项，系统性地清理代码中的“坏味道”，如重复代码、过时注释、不合理的命名等。
2.  **完善可观测性**：在Phase 3缓存监控的基础上，引入结构化日志（如Serilog），并将应用日志、性能指标等统一到可查询的平台，提升问题排查效率。
3.  **UI现代化评估**：在系统已长期稳定运行的前提下，可重新启动对引入第三方UI组件库的评估，以进一步提升用户体验。

## 4. 结论

本报告提出的技术路线，核心思想是**“收敛”与“深化”**。我们不寻求引入新的、颠覆性的技术，而是将现有技术栈的优势发挥到极致。通过**锁定一个稳定、务实的技术核心**，并将精力聚焦于**解决实际问题（修复BUG、重构代码、提升质量）**，我们能够以最小的风险和最高的效率，推动项目健康、可持续地向前发展。
