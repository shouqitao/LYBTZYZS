## 📋 重构背景

经过对现有代码的深入分析，发现原有的实体设计存在以下问题：
1. DiagnosisTreatment 和 Records 功能重叠
2. 诊疗流程不够清晰
3. 排队系统分散，缺乏统一管理
4. 部分命名不够贴切（如Billing、FormulaTemplates）

## 🏗️ 新架构核心设计

### 1. 核心聚合根：MedicalCase

**MedicalCase（医疗案例）** 作为整个诊疗流程的聚合根，管理从挂号到治疗结束的完整生命周期。

```csharp
public class MedicalCaseModel
{
    public Guid Id { get; set; }
    public Guid PatientId { get; set; }
    public Guid DoctorId { get; set; }
    
    // 关联各个阶段
    public virtual RegistrationModel? Registration { get; set; }
    public virtual ConsultationModel? Consultation { get; set; }
    public virtual TreatmentPlanModel? TreatmentPlan { get; set; }
    
    // 状态流转
    public MedicalCaseStatus Status { get; set; }
}
```

### 2. 统一排队管理：Queueing

**设计理念**：统一管理所有排队场景（看诊、收银、取药、理疗）

```csharp
public enum QueueType
{
    Consultation = 1,    // 看诊排队
    Payment = 2,        // 收银排队
    Pharmacy = 3,       // 取药排队
    Therapy = 4,        // 理疗排队
}
```

### 3. 专业看诊记录：Consultation

**Consultation** 替代原有的 DiagnosisTreatment，提供更专业的中医四诊记录功能。

### 4. 现代化治疗方案：TreatmentPlan

采用 **Owned Types** 设计，包含处方和理疗两部分，分别由药房和治疗室处理。

## ❌ 删除实体清单

### 确定删除
1. **DiagnosisTreatment/** 全部文件
   - DiagnosisTreatmentModel.cs → 被 ConsultationModel 替代
   - FormulaModel.cs → 功能整合到 TreatmentPlan
   - HerbItemModel.cs → 功能整合到 TreatmentPlan
   - TreatmentItemModel.cs → 功能整合到 TreatmentPlan

2. **Records/RecordModel.cs**

## 🔗 业务流程设计

### 主流程
```
挂号(Registration) 
→ 创建医疗案例(MedicalCase) 
→ 入队看诊(Queueing.Consultation)
→ 看诊(Consultation) 
→ 制定治疗方案(TreatmentPlan)
→ 入队收银(Queueing.Payment)
→ 收银(Cashier)
→ 根据方案分流：
   - 处方 → 入队取药(Queueing.Pharmacy) → 药房(Pharmacy)
   - 理疗 → 入队理疗(Queueing.Therapy) → 治疗室(TreatmentRoom)
```

### 排队系统流转
- 挂号后 → 自动入队看诊
- 看诊后 → 自动入队收银
- 缴费后 → 根据治疗方案自动入队（取药/理疗）
- 全程可追踪，统一管理

## 🎯 关键决策记录

### 1. 为什么使用 MedicalCase 作为聚合根？
- 符合领域驱动设计（DDD）原则
- 完整跟踪患者的整个就诊过程
- 便于状态管理和流程控制

### 2. 为什么要统一排队系统？
- 提升患者体验，全程可追踪
- 代码复用，降低维护成本
- 便于实现智能调度和优化

### 3. 为什么删除 DiagnosisTreatment？
- Consultation 提供更专业的中医四诊功能
- 避免功能重叠和概念混淆
- 新架构职责更清晰

## 📝 迁移建议

### 数据迁移
1. Records 数据 → 迁移到 MedicalCase + Consultation
2. DiagnosisTreatment 数据 → 迁移到 Consultation
3. Billing 数据 → 迁移到 Cashier

### 代码迁移
1. 先实现新实体和服务
2. 编写数据迁移脚本
3. 逐步替换旧代码引用
4. 完成后删除旧代码
