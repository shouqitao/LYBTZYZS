# 模块功能定位分析

## 1. Auth模块（身份认证）
**当前功能**：
- JWT令牌生成与验证
- 登录/登出
- 密码加密与验证
- SysAdmin特殊处理

**是否合理**：✅ 合理
**建议**：功能单一明确，保持现状

---

## 2. Users模块（用户管理）
**当前功能**：
- 用户CRUD操作
- 角色权限管理
- 用户状态管理
- 部门职位信息

**是否合理**：✅ 合理
**建议**：
- 可考虑将角色权限独立为Roles模块
- 但对小型诊所系统，合并在Users中也可接受

---

## 3. Patients模块（患者档案）
**当前功能**：
- 患者信息CRUD
- 过敏史记录
- 联系方式管理
- 就诊记录关联

**是否合理**：✅ 合理
**潜在问题**：
- 与MedicalCase的关系需要明确
- 建议：Patients管理基础信息，MedicalCase管理就诊记录

---

## 4. Doctors模块（医生管理）
**当前功能**：
- 医生信息CRUD
- 专长领域
- 执业证号
- 排班信息（？）

**是否合理**：⚠️ 需要明确
**问题**：
- 排班功能是否应该在这里？
- 建议：考虑独立Schedule模块或放入Registration中

---

## 5. Registration模块（挂号预约）
**当前功能**：
- 挂号登记
- 预约管理
- 号源管理
- 挂号费用

**是否合理**：✅ 合理
**建议**：
- 可以包含医生排班功能
- 与Queueing模块需要紧密配合

---

## 6. Queueing模块（排队叫号）
**当前功能**：
- 就诊排队
- 取药排队

**优点**：

**优点**：
- 作为聚合根设计优秀

## 总体评价

### 优秀的设计
1. **MedicalCase作为聚合根**：非常好的DDD设计
2. **统一的Queueing系统**：解决多场景排队需求
3. **中医特色模块**：Formula、Herbs、四诊信息

### 需要明确的问题

1. **TreatmentPlan vs Prescriptions**
   - 建议：TreatmentPlan = 总体方案（包含处方+理疗）
   - Prescriptions = 详细处方管理

2. **Herbs vs Pharmacy库存**
   - 建议：Herbs = 库存主数据
   - Pharmacy = 发药时的库存操作

3. **医生排班归属**
   - 建议：放在Registration模块中
   - 作为号源管理的一部分

### 模块依赖关系
```
基础层：Auth → Users
人员层：Patients, Doctors  
药材层：Herbs → Formula
流程层：Registration → Queueing → MedicalCase
核心层：MedicalCase → Consultation → TreatmentPlan → Prescriptions
执行层：Cashier, Pharmacy, TreatmentRoom
```

### 开发优先级建议
1. **必须先开发**：Auth, Users, Patients, Doctors, Herbs
2. **核心功能**：Registration, MedicalCase, Consultation, Prescriptions
3. **完整流程**：Queueing, Cashier, Pharmacy
4. **增值功能**：Formula, TreatmentPlan, TreatmentRoom

## 结论
整体模块设计合理，符合中医诊所业务特点。只需要明确少数模块间的职责边界即可。
