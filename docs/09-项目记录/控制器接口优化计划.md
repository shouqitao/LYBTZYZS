# 控制器接口优化计划

## 问题分析总结

### 主要问题
1. **接口重复**：多个控制器存在功能重复的接口
2. **RESTful设计不一致**：混合使用传统API和RESTful设计
3. **功能冗余**：状态管理、查询等功能存在多个重复接口
4. **未实现功能**：许多接口只是占位符，未实际实现

### 具体问题清单

#### 1. UsersController
**重复接口**:
- `GetPaged` (POST /paged) vs `GetUsers` (GET /) - 分页查询
- `Add` (POST /add) vs `CreateUser` (POST /) - 创建用户
- `Update` (PUT /update) vs `UpdateUser` (PUT /{id}) - 更新用户
- `GetById` (GET /getById/{id}) vs `GetUser` (GET /{id}) - 获取用户详情

**冗余功能**:
- `Disable`、`Enable`、`ToggleStatus` - 状态管理重复

#### 2. PatientsController
**重复接口**:
- `Add` (POST /add) vs `CreatePatient` (POST /) - 创建患者
- `GetPaged` (POST /paged) vs `GetPatients` (GET /) - 分页查询
- 状态管理：`Enable`、`Disable`、`ToggleStatus`、`DeletePatient`(实际是禁用)

**未实现功能**:
- 批量操作接口（返回count=0）
- 导入导出功能（占位符）
- 历史病历功能（TODO注释）

#### 3. HerbsController
**重复接口**:
- `GetList` (GET /) vs `GetPaged` (POST /paged) - 分页查询
- `GetActive` vs `GetAvailable` - 获取可用药材
- `Add` (POST /add) vs 隐含的RESTful创建

**冗余功能**:
- 状态管理：`Enable`、`Disable`、`ToggleStatus`、`UpdateStatus`

#### 4. FormulasController
- 相对简洁，基本遵循RESTful设计
- 主要问题：控制器名称应为FormulaController（单数）

## 优化策略

### 1. 统一RESTful设计原则
- 采用标准RESTful路由：GET, POST, PUT, DELETE
- 移除重复的自定义路由接口
- 统一HTTP状态码和响应格式

### 2. 接口清理规则
- **保留RESTful标准接口**：GET /, GET /{id}, POST /, PUT /{id}, DELETE /{id}
- **保留必要的特殊接口**：状态切换、批量操作等
- **移除重复接口**：删除功能重复的接口
- **移除未实现接口**：删除只有占位符的接口

### 3. 状态管理统一化
- 统一使用 `PATCH /{id}/status` 接口
- 移除单独的 Enable/Disable 接口
- 保留 ToggleStatus 作为便捷接口

### 4. 命名规范化
- 控制器名称使用单数：FormulaController, HerbController
- 接口方法名遵循RESTful约定
- 参数和响应模型标准化

## 优化实施顺序

1. **UsersController** - 问题最多，优先处理
2. **PatientsController** - 清理未实现功能
3. **HerbsController** - 简化状态管理
4. **FormulasController** - 重命名和微调
5. **其他控制器** - 按需优化
6. **前端API服务** - 同步更新
7. **测试验证** - 确保功能正常

## 预期效果

### 代码质量提升
- 接口清晰，职责明确
- 遵循REST设计原则
- 减少冗余代码

### 维护性改善
- 统一的接口设计
- 更好的可读性
- 减少学习成本

### 性能优化
- 移除无用代码
- 减少接口调用复杂度
- 优化缓存策略

## 风险评估

### 潜在影响
- 前端调用需要同步更新
- 可能影响现有功能测试
- 需要更新API文档

### 缓解措施
- 分步骤实施，逐步验证
- 保留向后兼容性（必要时）
- 充分测试每个变更
