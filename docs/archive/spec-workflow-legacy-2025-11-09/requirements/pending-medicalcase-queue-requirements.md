## 📋 功能概述

### 业务价值

在患者选择界面增加"待看诊队列"，帮助医生快速找到需要继续看诊的患者，提升工作效率，避免遗漏未完成的医案。

### 用户故事

**作为** 医生
**我希望** 在患者选择界面看到待看诊队列
**以便** 快速找到有未完成医案的患者，优先完成这些患者的诊疗

**作为** 医生
**我希望** 可以选择继续看诊、新建医案或关闭医案
**以便** 灵活处理患者的不同诊疗需求

**作为** 医生
**我希望** 界面布局清晰、交互便捷
**以便** 在1080P屏幕上高效工作，最小化视线移动

## 🎯 业务目标

### 解决的问题

**当前痛点**：
1. ❌ 医生需要在患者列表中搜索，无法快速找到有未完成医案的患者
2. ❌ 无法一眼识别哪些患者有待看诊的医案
3. ❌ 继续看诊时，诊断和处方数据未加载（Issue #1570）
4. ❌ 暂存后导航错误，无法继续编辑（Issue #1569）
5. ❌ 新建医案时，旧医案的诊断和处方未删除（Issue #1571）
6. ❌ 返回按钮导航错误（Issue #1573）
7. ❌ 界面布局单一，缺少患者信息快速预览

**期望效果**：
1. ✅ 待看诊队列优先显示，医生快速选择
2. ✅ 三区域布局（1080P优化），信息分层清晰
3. ✅ 患者信息详情模块，快速预览关键信息
4. ✅ 完整的医案生命周期管理（创建/更新/删除/暂存同步）
5. ✅ 流畅的导航流程，正确加载数据
6. ✅ 本地缓存优化，避免重复查询

### 业务规则

1. **医案优先级**：未完成医案 > 已挂号患者（未来扩展）
2. **排序规则**：
   - 未完成医案：按创建时间升序（先开始看诊的在前）
   - 已挂号患者：按挂号号码升序（号小的在前）
3. **医案生命周期**：
   - MedicalCase（医案）作为聚合根
   - Consultation（诊断）作为子实体
   - Prescription（处方）作为子实体
   - 医案关闭时，自动级联删除诊断和处方
4. **待看诊队列判断逻辑**（⚠️ 关键）：
   - 检查 PendingMedicalCaseDto.MedicalCaseId 是否为 null
   - 如果 **有值** → 暂存医案 → 继续看诊（Action="Continue"）
   - 如果 **为null** → 已挂号（未来） → 新建医案（Action="CreateNew"）

## 🖥️ UI设计规范

### 屏幕分辨率

**目标分辨率**：1080P（1920x1080），内容区约1760x940

### 布局结构（三区域）

```
┌────────────────────────────────────────────────────────────┐
│ 标题栏（患者选择）                                            │
├──────────────┬─────────────────────────────────────────────┤
│              │                                             │
│ [患者信息]    │  [搜索区域]                                  │
│ 300px x 180px│  - 搜索框 + 🔍搜索 + 新建患者 + 开始诊断      │
│              │                                             │
│ 姓名、手机号  │  [全部患者DataGrid]                          │
│ 年龄、地址    │  - 支持单击选中 + 双击开始诊断                │
│ 过敏史        │  - 移除行内“选择”按钮                         │
│              │                                             │
├──────────────┤  [分页控件]                                  │
│              │  - 每页20条                                  │
│ [待看诊队列]  │                                             │
│ 300px x 740px│  [提示信息]                                  │
│              │                                             │
│ - 姓名       │                                             │
│ - 手机号脱敏 │                                             │
│ - 状态       │                                             │
└──────────────┴─────────────────────────────────────────────┘
   左侧300px          右侧1460px
```

**设计优势**：
- 左侧 = 结果区（患者信息详情 + 待看诊快捷入口）
- 右侧 = 操作区（搜索 + 浏览全部患者）
- 符合“输入→输出”认知模型
- 最小视线移动距离（高频场景优先）

## 📊 优先级和时间估算

### 优先级

**P1 - 高优先级**

**理由**：
- 影响医生日常工作效率
- 修复多个已知Bug（Issue #1569, #1570, #1571, #1573）
- 为未来挂号功能预留接口

### 时间估算

**预估开发时间**：9-10小时

**拆分建议**：
- Phase 1：UI改造（双列表布局）- 2-3小时
- Phase 2：智能路由（继续看诊逻辑）- 2小时
- Phase 3：数据同步（修复Issue #1570, #1571）- 2小时
- Phase 4：导航修复（修复Issue #1569, #1573）- 1小时
- Phase 5：Server端API（待看诊队列查询）- 2小时

**建议工作流**：
- 由于时间估算>2小时且涉及UI改造，建议创建Epic分支
- 按Phase顺序实施，每个Phase完成后进行验证
- 全部完成后进行完整的运行时验证
- 验证通过后创建PR，在1-3天内合并

## 📝 术语说明

| 术语 | 说明 |
|-----|------|
| **MedicalCase（医案）** | 聚合根，管理Consultation和Prescription的完整生命周期 |
| **Consultation（诊断）** | MedicalCase的子实体，记录诊断信息（主诉、诊断结果等） |
| **Prescription（处方）** | MedicalCase的子实体，记录处方信息（药材、剂量等） |
| **看诊流程** | 医生接诊患者 → 创建/继续医案 → 记录诊断 → 开具处方 → 完成/暂存 |
| **当前选中患者** | 患者选择界面中被选中的患者，显示在患者详情模块中 |
| **级联删除** | 医案关闭时，自动删除关联的诊断和处方数据 |
