## 1. 项目背景

### 1.1 业务现状

传统中医看诊遵循"望闻问切→辨证→论治"的完整流程，当前系统已实现：

- **患者管理模块** (LYBT.Desktop.Patients)：患者基本信息管理
- **病案管理模块** (LYBT.Desktop.MedicalCase)：病案记录管理
- **辨证管理模块** (LYBT.Desktop.Consultation)：四诊和辨证分析
- **处方管理模块** (LYBT.Desktop.Prescriptions)：处方开具和管理

### 1.2 存在的问题

1. **流程割裂**：医生需要在多个模块间切换完成一次完整看诊
2. **操作繁琐**：每个模块单独打开，数据关联需要手动建立
3. **信息孤岛**：辨证和开方分离，缺乏上下文联动
4. **效率低下**：重复录入患者信息，无法快速参考历史

### 1.3 解决方案

开发一个**集成化的临床工作台**,在单一界面完成从患者选择、病案创建、四诊录入、辨证分析到处方开具的完整流程,提升医生工作效率。

**核心架构**:
- 病案(MedicalCase)是核心实体,辨证(Consultation)和处方(Prescription)都基于病案展开
- 复用独立的患者选择器组件(patient-selector),通过事件解耦
- 集成化界面设计,减少模块切换

## 2. 目标用户

### 2.1 主要用户

- **中医师**：门诊医生，负责诊断和开方

### 2.2 用户画像

- **姓名**：张医生
- **年龄**：35-50岁
- **职业**：中医门诊医生
- **工作场景**：每天接诊20-40位患者，平均每位患者15-20分钟
- **技能水平**：熟悉传统中医诊疗流程，计算机使用水平中等
- **痛点**：
  - 在多个软件模块间切换浪费时间
  - 录入信息时无法同时查看历史病案
  - 开处方时需要回看辨证结果，但界面已切换

### 2.3 使用场景

#### 场景1：新患者首诊
1. 患者到达诊室，医生查询或创建患者档案
2. 创建新病案，录入主诉和现病史
3. 进行四诊（望、闻、问、切），记录体征
4. 综合分析，得出中医诊断、证型和治则
5. 根据病情决定是否开具处方
6. 如需开方，选择药材、设置剂量和剂数
7. 保存完整看诊记录

#### 场景2：复诊患者
1. 选择患者，查看历史病案列表
2. 参考上次辨证结果和用药
3. 创建新病案，记录本次情况
4. 对比前后变化，调整治疗方案
5. 完成看诊

#### 场景3：只辨证不开方
1. 患者症状轻微或处于观察期
2. 完成四诊和辨证分析
3. 给出调理建议但不开药
4. 直接完成看诊，不进入处方流程

## 3. 功能需求

### 依赖说明

本需求依赖 **patient-selector (SPEC-2025-002)** 组件,该组件提供:
- 患者搜索功能(姓名模糊匹配、手机号精确匹配)
- 快速创建新患者功能
- 患者选择确认
- 通过 `PatientSelectedEvent` 发布患者选择事件

**事件契约**:
```csharp
namespace LYBT.Desktop.Common.Events;

public class PatientSelectedEvent : PubSubEvent<PatientSelectedPayload> { }

public class PatientSelectedPayload
{
    public Guid PatientId { get; set; }              // 患者ID(核心标识)
    public string PatientName { get; set; }          // 患者姓名
    public string Gender { get; set; }               // 性别
    public int? Age { get; set; }                    // 年龄
    public string PhoneNumber { get; set; }          // 手机号
    public DateTime? LastVisitDate { get; set; }     // 上次就诊日期
    public int VisitCount { get; set; }              // 就诊次数
    public string? AllergyHistory { get; set; }      // 过敏史
    public DateTime SelectedAt { get; set; }         // 选择时间戳
}
```

### FR1: 患者信息展示与病案加载

**优先级**：P0(必须)

**描述**：
工作台左栏嵌入 `PatientSelectorControl` 组件,订阅 `PatientSelectedEvent` 事件,在患者选择后:
- 显示患者信息卡片(姓名、性别、年龄、联系方式、过敏史)
- 加载并显示患者历史病案列表(最近10条)
- 启用"新建病案"按钮

**验收标准**：
- [x] 工作台正确嵌入 PatientSelectorControl 组件
- [x] 正确订阅 PatientSelectedEvent 事件
- [x] 接收到事件后显示患者信息卡片
- [x] 自动加载患者历史病案列表(按就诊日期倒序)
- [x] 历史病案列表显示：日期、主诉、诊断状态
- [x] 如有过敏史,以红色高亮提示
- [x] 启用"新建病案"按钮

**技术约束**：
- 使用 Prism EventAggregator 订阅事件
- 历史病案通过 `IMedicalCaseRepository.GetByPatientIdAsync()` 查询
- 使用 AutoMapper 映射 Dto → Item

### FR2: 病案创建

**优先级**：P0（必须）

**描述**：
- 为选中患者创建新病案
- 录入主诉（ChiefComplaint）和现病史（PresentIllness）
- 自动生成病案编号

**验收标准**：
- [x] 点击"新建病案"弹出录入对话框
- [x] 主诉为必填项，长度1-200字符
- [x] 现病史为可选项，长度≤2000字符
- [x] 保存后自动创建 `MedicalCase`，状态为 `Active`
- [x] 自动进入辨证录入界面

**数据模型**：
```csharp
MedicalCaseItem {
    PatientId: Guid (必填)
    ChiefComplaint: string (必填, 1-200)
    PresentIllness: string (可选, ≤2000)
    Status: MedicalCaseStatus.Active
}
```

### FR3: 四诊录入

**优先级**：P0（必须）

**描述**：
- 录入望诊（Inspection）：神、色、形、态、舌象
- 录入闻诊（Auscultation）：语音、呼吸、气味
- 录入问诊（Inquiry）：寒热、汗、痛、饮食、二便、睡眠等
- 录入切诊（Palpation）：脉象、按诊

**验收标准**：
- [x] 四诊各项支持多行文本输入
- [x] 四诊可单独保存（草稿）
- [x] 至少填写两项四诊才能进入辨证分析
- [x] 输入框失焦后显示已保存状态

**数据模型**：
```csharp
ConsultationItem {
    MedicalCaseId: Guid (关联)
    Inspection: string (可选, ≤500)
    Auscultation: string (可选, ≤500)
    Inquiry: string (可选, ≤1000)
    Palpation: string (可选, ≤500)
    Status: ConsultationStatus.InProgress
}
```

**备注**：
- MVP阶段仅支持纯文本输入
- Phase 2 增加常用词条快速选择（如舌象：淡红、红、绛红等）

### FR4: 辨证分析

**优先级**：P0（必须）

**描述**：
- 录入中医诊断（TcmDiagnosis）
- 录入证型（Syndrome）
- 录入治则（TreatmentPrinciple）

**验收标准**：
- [x] 三项均为必填项
- [x] 中医诊断：1-100字符
- [x] 证型：1-50字符
- [x] 治则：1-200字符
- [x] 点击"完成辨证"后 `Consultation` 状态变为 `Completed`
- [x] 完成辨证后自动启用处方区

**数据模型**：
```csharp
ConsultationItem {
    TcmDiagnosis: string (必填, 1-100)
    Syndrome: string (必填, 1-50)
    TreatmentPrinciple: string (必填, 1-200)
    Status: ConsultationStatus.Completed
    CompletedAt: DateTime
}
```

### FR5: 处方开具（可选）

**优先级**：P0（必须）

**描述**：
- 辨证完成后，医生可选择"开具处方"或"完成看诊（不开方）"
- 如选择开方，进入处方录入区
- 支持添加药材、设置剂量、剂数、用法
- 自动计算单剂和总价

**验收标准**：
- [x] 只有辨证完成后才能开处方
- [x] 药材列表支持搜索和添加
- [x] 每味药材需填写：药材名、剂量、单位
- [x] 自动从 `IHerbRepository` 获取单价
- [x] 自动计算：单剂金额 = Σ(剂量 × 单价)，总金额 = 单剂金额 × 剂数
- [x] 剂数范围：1-100
- [x] 单味药材剂量范围：>0, ≤1000g
- [x] 至少添加1味药材
- [x] 点击"完成处方"后 `Prescription` 状态变为 `Completed`

**数据模型**：
```csharp
PrescriptionItem {
    MedicalCaseId: Guid (关联)
    ConsultationId: Guid (关联)
    Doses: int (必填, 1-100)
    Usage: string (可选, 如"水煎服")
    Frequency: string (可选, 如"每日两次")
    TotalAmount: decimal (自动计算)
    Status: PrescriptionStatus.Draft -> Completed
    Herbs: List<PrescriptionHerbItem> (至少1味)
}

PrescriptionHerbItem {
    HerbId: Guid
    HerbName: string
    Dosage: decimal (>0, ≤1000)
    Unit: string (如"g")
    UnitPrice: decimal (从Herb获取)
    Subtotal: decimal (自动计算 = Dosage × UnitPrice)
}
```

### FR7: 完整看诊流程

**优先级**：P0（必须）

**描述**：
- 支持完整的看诊流程：患者选择 → 病案创建 → 四诊 → 辨证 → 处方（可选）→ 完成
- 支持两种结束方式：
  1. 辨证完成 + 处方完成 → 完成看诊
  2. 辨证完成 + 不开方 → 完成看诊

**验收标准**：
- [x] 流程指示器显示当前阶段（病案→辨证→处方→完成）
- [x] 完成看诊后 `MedicalCase` 状态变为 `Closed`
- [x] 完成看诊后工作台重置，可开始下一位患者

**状态流转图**：
```
MedicalCase: Active → Closed
Consultation: InProgress → Completed
Prescription: Draft → Completed (可选)
```

## 4. 非功能需求

### NFR1: 性能要求

**优先级**：P0

- 界面加载时间 ≤ 1秒
- 搜索患者响应时间 ≤ 500ms
- 保存操作响应时间 ≤ 1秒
- 药材搜索响应时间 ≤ 300ms

### NFR2: 可用性要求

**优先级**：P0

- 界面布局清晰，信息分区明确
- 流程符合医生操作习惯（左→中→右）
- 必填项有明确标注（*）
- 操作反馈及时（保存成功提示）
- 错误提示友好（标注错误字段）

### NFR3: 可靠性要求

**优先级**：P0

- 数据不丢失：离开页面前未保存数据提醒
- 网络异常：自动重试3次，失败后提示
- 并发冲突：版本检查，冲突时提示刷新

### NFR4: 可维护性要求

**优先级**：P0

- 严格遵循 MVVM 三层架构
- 使用 AutoMapper 进行 Dto ↔ Model 转换
- 依赖注入管理依赖关系
- 代码符合 `unified-design-standard.md` 规范

### NFR5: 可扩展性要求

**优先级**：P1

- 预留 AI 辅助诊断接口
- 预留打印功能接口
- 预留常用方剂模板接口
- 支持后续添加自定义字段

## 5. 约束条件

### 5.1 技术约束

1. **架构约束**：
   - 必须遵循 MVVM 三层架构
   - 使用 Prism 框架（Region、EventAggregator、Command）
   - 使用 MaterialDesignInXaml 界面库

2. **数据模型约束**：
   - 使用现有 `MedicalCaseItem`、`ConsultationItem`、`PrescriptionItem`
   - 不修改现有 Dto 定义
   - 通过 AutoMapper 映射 Dto ↔ Item

3. **API约束**：
   - 使用现有 Repository 接口
   - 不修改 Server 端 API
   - 通过现有接口完成所有操作

### 5.2 业务约束

1. **数据完整性**：
   - 一个 `MedicalCase` 必须关联一个 `Consultation`
   - `Prescription` 可选，但如果存在必须关联 `MedicalCase` 和 `Consultation`
   - 不支持删除已完成的记录

2. **权限约束**：
   - MVP 阶段不考虑权限控制
   - Phase 2 增加角色权限（医生/药师）

3. **并发约束**：
   - MVP 阶段假设单工作站操作
   - Phase 2 增加乐观锁（版本号）

### 5.3 时间约束

- MVP 开发周期：2-3周
- 测试周期：1周
- 上线时间：2025年2月

## 10. 风险与缓解

### 风险1：医生操作习惯差异大

**风险等级**：中

**影响**：部分医生可能不适应三栏集成布局

**缓解措施**：
- MVP 上线前进行用户测试，收集反馈
- 提供新手向导和操作视频
- Phase 2 考虑提供自定义布局选项

### 风险2：历史数据迁移复杂

**风险等级**：低

**影响**：现有数据可能不完整（如缺少 ConsultationId）

**缓解措施**：
- 工作台只处理新创建的病案
- 历史数据通过原有模块查看
- 提供数据修复工具（可选）

### 风险3：性能问题

**风险等级**：低

**影响**：患者历史病案过多时加载慢

**缓解措施**：
- 历史列表分页加载（默认最近10条）
- 使用虚拟化列表（VirtualizingStackPanel）
- 缓存常用数据（症状词条、药材列表）

### 风险4：并发冲突

**风险等级**：低（MVP阶段）

**影响**：多工作站同时操作同一患者

**缓解措施**：
- MVP 阶段假设单工作站
- Phase 2 增加乐观锁（版本号）
- 提供冲突检测和提示
