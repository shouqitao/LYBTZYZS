> 版本: v1.0 | 日期: 2026-08-08 | 维护者: 技术总监

> 关联: `02-ssot-architecture.md`（信息点唯一权威）｜`03-architecture/01-system-overview.md` §技术栈全景（技术栈合理性评估）｜Skill `lybtzys-coder-rules`（agent 操作规则）

## 一、核心原则

> **① 先文档后代码**：任何技术方案变更，先更新权威文档（字典），再按文档改代码。禁止跳过文档直接改代码。
> **② 文档是字典，不是过程**：文档定义系统「应该是什么」（当前态/设计态），不是「怎么做/做过什么」（过程）。过程记录（审计报告、任务书、分析）是历史，统一归档 `docs/compose/`，不进入正式文档目录。
> **③ 不随意引入**：新技术引入必须走流程——深度分析 → 有依据 → 修改方案文档 → 审批 → 才能使用。

---

## 二、技术方案变更分级

| 级别 | 定义 | 流程 |
|------|------|------|
| **T0 文档维护** | 蓝图/架构文档记录与实际偏差（文件数、命名、接线状态） | 直接改文档，无需审批 |
| **T1 方案收敛** | 多套方案并存 → 统一为一套（删死代码/合并重复机制） | 技术总监分析 → 用户确认方向 → 任务书 → 执行 |
| **T2 方案调整** | 既有技术/模式的方向性调整（如 Service/Handler 边界、DbContext 归属） | 技术总监分析（含边际情况）→ 用户拍板 → **先改蓝图/ADR** → 任务书 → 执行 |
| **T3 引入新技术** | 新增依赖包、新框架、新设计模式 | **完整流程**（见 §三） |

## 三、引入新技术流程（T3，强制）

```
① 需求触发 ── 明确要解决什么问题（不解决问题不引入）
    │
② 深度分析 ── 对照蓝图 §0.5 评估框架 4 标准：
    │          · 必要性（不可替代职责？现有技术能否解决？）
    │          · 活跃度（生态成熟度、社区使用、维护状态）
    │          · 替代成本（迁移工作量、学习成本）
    │          · 复杂度预算（引入后认知负担是否可控）
    │          另须：候选方案对比（≥2 个，含"不引入"选项）、
    │               安全/许可/版本兼容性核查
    │
③ 有依据 ──── 产出分析报告（存 docs/compose/reports/）：
    │          · 候选对比表 + 推荐项 + 理由
    │          · 对现有架构的影响面（哪些模块会动）
    │          · 失败回退方案
    │
④ 修改方案文档 ── 用户确认后，先更新权威文档：
    │          · 蓝图 §0.5 技术栈全景表（加入新技术）
    │          · 相关架构文档/ADR（设计态定义）
    │          · AGENTS.md 技术栈速览（如有）
    │
⑤ 审批 ──── 用户拍板（是/否/调整）
    │
⑥ 执行 ──── 派发 Mimo Code（任务书必须引用已更新的方案文档）
```

**禁止**：未经 ②③④⑤ 直接引包/写代码；分析报告未产出就改代码。

## 四、技术方案反复横跳的预防

**根因**：方案未文档化 → 每次分析得出不同结论 → 代码来回改。

**规则**：
1. **方向决策必须落文档**：任何 T1/T2 决策，拍板后 24h 内更新蓝图/ADR（§九 追加决策行），否则视为未决策
2. **文档是唯一基线**：代码与文档冲突时，以文档（设计态）为准；禁止"先改代码再补文档"
3. **已定案不反复**：用户已拍板的方案（如 MedicalCase Service 化、7 DbContext、用户自主切换）不因新审计重新质疑，除非有新的强证据且走 T2 流程
4. **历史报告不误导**：过时/被推翻的报告留在 compose/（历史），正式文档只反映当前态；查阅时以正式文档为权威，不以历史报告为准

## 五、文档目录边界（字典 vs 过程）

| 目录 | 定位 | 放什么 |
|------|------|--------|
| `docs/00-governance/` | 治理规则（字典） | 命名规范、SSOT 架构、本规则 |
| `docs/01-product/` | 产品定义（字典） | 愿景、画像、术语、权限 |
| `docs/02-requirements/` | 业务规则（字典） | 模块需求、US/BR |
| `docs/03-architecture/` | 架构当前态（字典） | 架构文档、蓝图、总账、ADR |
| `docs/04-api-reference/` | API 契约（字典） | 端点契约 |
| `docs/05-development/` | 开发标准（字典） | 编码规范、测试标准 |
| `docs/06-operations/` | 运维手册（字典） | 部署、配置、监控 |
| `docs/compose/{plans,reports,specs}/` | **过程归档（非字典）** | 任务书、审计报告、分析、计划 |

**判定标准**：一份文档描述"系统现在应该是什么" → 正式目录（字典）；描述"某次分析/任务/历史过程" → compose（过程）。拿不准时问：**这份文档过 3 个月还要不要改？** 要改（跟着系统变）= 字典；不用改（记录历史）= 过程。

## 六、验证标准

1. 新引入依赖：`grep` 确认蓝图 §0.5 全景表已含该技术
2. 方案变更：确认蓝图/ADR/总账 §九 已先行更新（git log 顺序：docs 在前，代码在后）
3. 正式目录无过程文档：`docs/03-architecture/` 等目录 grep 不到 task/audit/report 类文件（已由 2026-08-08 文档收敛验证）
4. 每次任务书引用权威文档章节号（如「蓝图 §2.2」），不写"按上次讨论"
