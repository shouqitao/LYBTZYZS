# 需求验证清单 (Requirements Checklist)

**用途**: 验证需求文档的完整性、清晰性和可实施性
**适用阶段**: Requirements阶段完成后，Design阶段开始前
**强制级别**: 必选 (MUST) - 所有新功能开发和重大重构必须完成此清单

---

## 1. 需求定义清晰性 (Requirements Clarity)

### 1.1 问题陈述 (Problem Statement)
- [ ] **明确定义了要解决的问题** - 用户遇到的痛点是什么？
- [ ] **问题范围清晰** - 问题边界明确，不模糊
- [ ] **问题的影响已量化** - 影响多少用户？频率如何？严重程度？
- [ ] **当前解决方案的不足** - 为什么现有方案不够好？

### 1.2 用户价值 (User Value)
- [ ] **明确的用户受益** - 解决此问题后用户得到什么价值？
- [ ] **用户角色定义** - 哪些用户角色会使用此功能？（医生/管理员/患者）
- [ ] **用户故事完整** - 以"作为...我希望...以便..."格式描述
- [ ] **优先级说明** - 是MVP必需(P0)还是增强功能(P1/P2)？

### 1.3 验收标准 (Acceptance Criteria)
- [ ] **可测试的验收标准** - 每个标准都可以验证通过/失败
- [ ] **覆盖正常路径** - 主流程的验收标准完整
- [ ] **覆盖异常路径** - 错误处理、边界条件的验收标准
- [ ] **性能指标** - 如有性能要求，已定义可测量的指标（响应时间≤2秒等）

---

## 2. 范围管理 (Scope Management)

### 2.1 范围边界 (Scope Boundaries)
- [ ] **明确包含的功能** - 列出在范围内的功能清单
- [ ] **明确排除的功能** - 列出显式不包含的功能（避免范围蔓延）
- [ ] **与MVP对齐** - 检查是否符合MVP定义的范围
- [ ] **无过度设计** - 没有超出实际需求的投机性功能

### 2.2 依赖关系 (Dependencies)
- [ ] **依赖的现有功能已识别** - 列出需要依赖的现有模块/功能
- [ ] **依赖的数据模型已识别** - 需要的数据表/DTO/Enum等
- [ ] **依赖的外部服务已识别** - 数据库/API/第三方库等
- [ ] **阻塞因素已识别** - 是否有前置任务必须先完成？

### 2.3 影响范围评估 (Impact Assessment)
- [ ] **影响的模块已识别** - Server/Client/Shared中哪些模块会受影响？
- [ ] **需要更新的文档已列出** - 架构文档/API文档/用户指南等
- [ ] **向后兼容性已评估** - 是否会破坏现有功能？迁移计划？
- [ ] **数据库变更已评估** - 是否需要Schema变更？迁移脚本？

---

## 3. Constitution合规性 (Constitution Compliance)

### 3.1 架构原则合规 (Architecture Principles)
- [ ] **符合三层对齐架构** - Server/Client/Shared层次清晰
- [ ] **依赖方向正确** - Controller→Service→Repository，View→ViewModel→Service
- [ ] **无技术黑名单违规** - 未使用Redis/CQRS/MediatR/Docker/GraphQL等禁用技术
- [ ] **依赖注入符合规范** - 仅使用构造函数注入，无ServiceLocator

### 3.2 MVP优先原则 (MVP-First Principle)
- [ ] **MVP必需性判断** - 问："这个功能MVP需要吗？"答案明确
- [ ] **够用即好** - 避免过度抽象，单一场景不需要抽象
- [ ] **增量优化** - 小步快跑，不是大规模重构
- [ ] **无投机性优化** - 无性能瓶颈不需要预先优化

### 3.3 开发流程合规 (Workflow Compliance)
- [ ] **Issue已创建** - GitHub Issue已创建并关联到Epic
- [ ] **Spec文档结构完整** - requirements.md存在且符合模板
- [ ] **文档同步计划** - 明确列出需要更新的文档清单
- [ ] **分支命名规范** - 计划使用`feature/{issue-id}-{description}`命名

---

## 4. 技术可行性 (Technical Feasibility)

### 4.1 技术方案初步评估 (Preliminary Technical Assessment)
- [ ] **技术栈符合项目标准** - .NET 8/EF Core/WPF/JWT等
- [ ] **已有技术能力评估** - 团队是否具备实现此需求的技术能力？
- [ ] **第三方依赖评估** - 是否需要引入新的NuGet包？是否经过审查？
- [ ] **技术风险识别** - 是否存在技术不确定性？需要POC吗？

### 4.2 数据模型初步评估 (Data Model Assessment)
- [ ] **实体关系初步定义** - 涉及哪些实体？关系如何？
- [ ] **数据完整性约束** - 外键/唯一约束/非空约束等
- [ ] **数据安全需求** - 是否涉及敏感数据（患者隐私/医疗数据）？
- [ ] **数据迁移需求** - 是否需要迁移现有数据？

---

## 5. 文档质量 (Documentation Quality)

### 5.1 需求文档结构 (Requirements Document Structure)
- [ ] **包含所有必需章节** - 问题陈述/用户价值/验收标准/范围/依赖等
- [ ] **语言清晰准确** - 使用中文，术语统一，无歧义
- [ ] **格式规范** - 使用Markdown，标题层级正确，列表格式统一
- [ ] **可读性良好** - 逻辑清晰，段落合理，适当使用表格/图示

### 5.2 可追溯性 (Traceability)
- [ ] **关联到Epic/Issue** - 明确标注GitHub Issue编号
- [ ] **关联到用户故事/需求** - 与product.md中的产品目标对齐
- [ ] **关联到Constitution** - 引用Constitution中的相关原则
- [ ] **版本信息完整** - 创建日期/版本号/作者等元数据
